# 專案 Markdown 文件與遊戲規劃審查

> **審查日期**：2026-10-15（Asia/Taipei）  
> **審查範圍**：審查時專案內 31 份 Markdown 檔案，涵蓋根目錄文件、`.agents/rules/`、`docs/overview/`、`docs/manual/`、`docs/plans/`、`docs/references/` 與 `docs/UI_PAGE_STRUCTURE.md`。  
> **目的**：提升文件可信度、維護穩定性、規劃效率，以及玩法和工程的可擴充性。  
> **限制**：這是文件內容與交叉一致性的審查，沒有逐項以程式碼、資料、測試或實際執行核實文件中的全部現況主張。涉及實作現況、效能數字及完成狀態的修改，應先對照對應證據。

## 摘要

專案已具備相當完整的文件層次：快速上手、玩法與架構概覽、前後端模組手冊、總待辦、工作任務、變更紀錄及 AI 協作規則。當前主要風險是同一資訊在多份文件重複維護，且規格、已實作現況、候選構想和歷史紀錄常以相似語氣呈現。時間一久，索引、數值、操作說明和路線圖會互相漂移，讓新成員與工具難以判斷哪份內容可信。

建議依序建立單一權威來源與文件狀態標記、清理失效連結和矛盾敘述、改善待辦的驗收格式，再以文件檢查及垂直玩法切片降低後續漂移。對多人、高併發、外掛熱載入等宏大架構，先列為有前置條件的遠期探索；近期規劃優先回答「玩家能做什麼、為何有趣、怎樣驗證」。

## 主要建議

### P0：建立可信的文件索引與權責

1. **修復連結並加入連結檢查。** `docs/plans/FUTURE_IMPROVEMENTS.md` 曾被發現有失效的審查稿及程式碼相對連結（參見既有 `docs/references/Copilot_Review.md`）。逐一確認每個連結的原意，修正、替換或標為已除役；不要只改成另一份同名審查稿。檢查器應涵蓋 Markdown 相對路徑、檔案大小寫及標題錨點，且在 CI 或本機提供檔名與行號。
2. **每類事實只保留一個權威來源。** 建議 `GEMINI.md` 放穩定協作與設計約束，`ARCHITECTURE.md` 放現行邊界與依賴，`ACTIVE_TASKS.md` 放正在執行的工作，模組手冊放經核對的模組契約，概覽文件負責導覽，`FUTURE_IMPROVEMENTS.md` 放候選工作，`CHANGELOG.md` 記錄已交付變更。參考審查稿提供建議，不自動成為已核准規格。
3. **標示內容狀態。** 使用一致狀態，例如「現行已驗證」、「已決議待實作」、「候選提案」、「歷史／已除役」。現況記錄核對日期及程式、資料或測試依據；提案用將來式並明確標記，避免讀者把藍圖當成已上線功能。
4. **整理重複路線圖。** 多份 M／FE 手冊都有未來演進章節，與中央總待辦內容重疊。完整候選工作集中在總待辦；手冊只保留模組現況、契約及必要的待辦連結。

### P1：提升遊戲規劃的可玩性與可驗收性

1. **以可玩閉環排序工作。** 把「城鎮整備 → 地牢探索 → 戰鬥決策 → 戰利品與成長 → 撤離／存檔」定義為核心垂直切片。每段寫明玩家目標、選擇、風險、回饋、失敗代價和完成條件；先驗證一段完整、有趣的流程，再擴大地圖與系統數量。
2. **從玩家問題出發描述功能。** 晝夜、天候、SAN 異化、詞綴、Gamepad、多人合作等提案應說明目標玩家、要改善的體驗、與核心循環的關係、依賴、成本、風險、原型方法及不做的範圍。先用低成本原型確認樂趣，再決定是否投入完整系統。
3. **把主張轉成測試。** 「更沉浸」、「更刺激」、「60 FPS」等不能單獨作為驗收標準。寫明測量環境、基線、目標和失敗條件；玩法可用小型玩家測試檢查意圖可讀性、選擇是否有差異、失敗是否可理解及探索資訊是否充分。
4. **把可用性和復原列入設計。** 新互動功能同步考慮鍵盤／手把操作、焦點與語意、色彩對比、減少動態效果、觸控尺寸、斷線後狀態復原及指令重送規則，避免事後補做。
5. **區分當前單機目標與遠期在線願景。** 將萬人併發、跨服、雲端同步、分散式 Actor、Protobuf、外掛熱載入等標成遠期探索，訂出觸發條件（明確多人需求、容量證據、部署與營運能力）再啟動。現階段維持可理解、可測試的模組化單體，降低不必要的複雜度。

### P1：讓規格更穩定、容易擴充

1. **建立共用遊戲詞彙表與資料契約。** 統一五維屬性、HP／MP／SAN 等資源、DamageType、元素家族、狀態標籤、Buff 分類、裝備槽位、方向和鍵位。明確區分「傷害類型」與「元素／狀態標籤」，避免把抗性、狀態效果和傷害類型混成同一分類。
2. **釐清跨文件不一致處。** 玩法概覽將傷害描述為「九大五行相生相剋」，但列出的物理類型及道法元素不易與「九大」對應；M3、M3-1 對傷害／元素分類亦有待統一。文件也交替提到六個前端模組、七個視圖區塊、七層 CSS，以及六個 CSS 拆分檔；鍵位、心跳週期、SaveData schemaVersion 和 Java／Spring 版本亦有多處陳述。建立一份權威表後，其他文件改為引用。
3. **以機制擴充取代無界資料化。** 遊戲數值、文案、標籤、掉落及組合規則適合由資料描述；新資源生命週期、新結算階段、新互動類型等改變執行語意的機制，仍應由程式碼實作並以契約擴充。將「100% 資料驅動」改成清楚的擴充邊界，避免把所有行為塞進難以驗證的通用解析器。
4. **為資料檔定義版本與驗證流程。** JSON 範例應對應正式 schema／DTO，列出必要欄位、預設值、範圍、未知欄位策略、版本遷移及錯誤回報。資料錯誤應在啟動或載入時定位到檔案與欄位，避免靜默 fallback 造成不一致狀態。
5. **將易變數值改為帶證據的快照。** 測試數量、檔案大小、FPS、封包節省百分比、模組數等都應附日期、環境和量測方法；未測量的數值明確標為目標，不寫成現行事實或永久保證。

### P2：降低日常維護成本

1. **固定提案／任務格式。** 總待辦每個項目至少有唯一 ID、玩家或工程問題、優先級、依賴、範圍與非目標、驗收條件、測試／量測方法、風險、狀態及完成證據。`ACTIVE_TASKS.md` 保持精簡，每項任務可獨立驗收，不複製整章規格。
2. **精簡長篇文件並採漸進揭露。** README 和導覽頁先提供啟動方式、核心循環、文件入口與已知限制；細節連到手冊。巨大總待辦按狀態與優先級建立索引，封存過期提案，避免讀者在長文中尋找當前決策。
3. **降低 AI 規則衝突與重複。** `GEMINI.md`、`.agents/rules/data_driven_architecture.md`、README Golden Rules 和架構文件都含規範性陳述。整理出短小的通用約束，將工具專用指令、設計理由、例外和完整示例放在各自位置；明確寫出規則衝突時的優先順序。
4. **使用生成或自動驗證的表格。** DTO、列舉、JSON 欄位、鍵位、CSS 載入順序等易漂移內容，優先從程式／資料產生，或建立輕量檢查驗證文件與實作一致。文件檢查分層導入：先連結與程式碼區塊，再視需要加入 JSON Schema 與契約核對。
5. **維持變更範圍相關。** 不要求每次改動重讀所有手冊；每份權威文件標清責任與關聯模組，讓索引能導引到受影響的章節。

## 文件群組觀察

|---|---|
| `README.md`、`docs/overview/` | README 有大量內嵌目錄和易過期徽章／狀態數字；概覽中的實作細節宜指向手冊，玩法目標和現況要分開。 |

| `docs/manual/`、`docs/UI_PAGE_STRUCTURE.md` | 先建立各手冊共同模板（責任、資料／事件契約、狀態轉移、錯誤情境、驗收依據），再統一詞彙與版本；將提案移回總待辦。 |

## 建議的一致性核對清單

- 傷害類型、元素家族、抗性與狀態標籤的 canonical 清單。
- 預設鍵位、操作場景、快捷鍵衝突、重新綁定與輸入焦點規則。
- MUD／DRPG／戰鬥的時間更新週期及其責任、時間來源與容許延遲。
- SaveData 現行 schema 版本、支援的遷移路徑與舊版退場政策。
- CSS 實際載入順序、樣式層級與畫面模組的命名區別。
- 支援的 Java、Spring Boot、瀏覽器、建置方式及測試基準。
- 文件內所有相對檔案連結、章節錨點、程式碼路徑與數據日期。

## 落地順序

1. 修正失效連結並設定文件權責；確保讀者能找到唯一的現行規格。
2. 決定狀態標籤與共同詞彙表，核對上方清單中的跨文件矛盾。
3. 將待辦整理為有玩家／工程問題、依賴及可驗收結果的候選工作，精簡重複 roadmap。
4. 為核心玩法設計一個可玩的垂直切片，以原型或玩家測試驗證後再擴大範圍。
5. 加入低成本文件防線，先檢查連結與格式，再逐步驗證資料範例和實作契約。

本文件提供審查建議，不代表建議已核准或功能已實作。採納項目應移至 `docs/plans/FUTURE_IMPROVEMENTS.md`，啟動後拆至 `ACTIVE_TASKS.md`；只有程式、資料及驗收依據確認後，才更新現況手冊與概覽。
