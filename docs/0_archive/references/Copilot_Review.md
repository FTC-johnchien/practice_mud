# 專案文件體系與遊戲規劃審查建議

> **審查日期**：2026-10-15
> **審查範圍**：審查時既有的 `docs/**/*.md`（24 份）及指定文件 `ACTIVE_TASKS.md`、`ARCHITECTURE.md`、`docs/UI_PAGE_STRUCTURE.md`。
> **審查目的**：提升文件正確性、維護效率、遊戲規劃品質與後續擴充能力。
> **文件定位**：本文件是審查結果與建議，不取代專案憲法、當前規格或總待辦；建議經決議後，依本文所列文件權責落地。

## 一、審查範圍

- `docs/overview/`：架構摘要、玩法概覽、模組地圖、前端佈局指南、快速上手。
- `docs/manual/`：後端 M1～M9（含 M3-1）及前端 FE-1～FE-6 全部模組手冊。
- `docs/plans/FUTURE_IMPROVEMENTS.md`、`docs/references/README.md`、`docs/UI_PAGE_STRUCTURE.md`。
- 根目錄指定文件：`ACTIVE_TASKS.md`、`ARCHITECTURE.md`。

審查以文件內部一致性、索引與相對連結、規格和提案的區隔、遊戲願景與工程路線的一致性為主；**沒有以程式碼或執行結果逐項驗證所有文件中的現況數值、類別位置、測試數與效能主張**。修改規範前，應以程式碼、資料檔、測試及實際部署設定核對。

## 二、總結

現有文件涵蓋面廣，已建立憲法、當前任務、架構、概覽、模組手冊、長期待辦及參考資料等層次，是良好的基礎。主要風險不是缺少文件，而是**同一事實散落多處且缺少自動校驗**：規格、已實作現況、歷史紀錄和腦力激盪提案容易混讀；前端、戰鬥、持久化的詞彙和數值有多份版本；大量模組手冊各自維護長篇未來藍圖，增加重複和過期機率。

建議先建立「權威來源、文件狀態標籤、可驗證連結」三項治理底座，再依垂直切片推進玩法；不要先把長期願景中的多人分散式、腳本熱載入、二進位協定或大規模效能改造當成近期承諾。

## 三、優先改善清單

### P0 — 修復文件索引與權威來源

1. **清除失效相對連結並建立自動檢查**：本報告寫入前執行的相對連結檢查，在 `FUTURE_IMPROVEMENTS.md` 找到 **17 個無法解析的相對連結**：8 個指向不存在的 `Copilot_Code_Review.md`，另 9 個程式碼／測試連結使用了錯誤的相對根路徑。這會讓待辦依據、程式碼錨點和審查來源無法追溯。逐一確認預期目標後修正、改指有效來源，或移除已失效引用；不要只把它們機械地改成本文檔名稱。
2. **為每一類資訊指定唯一權威文件**：建議採用下列責任分界：
   - `GEMINI.md`：不可違反的架構憲法與長期不變約束。
   - `ACTIVE_TASKS.md`：唯一當前執行中的微任務及其驗收條件。
   - `ARCHITECTURE.md`：現行系統邊界、依賴方向與工程不變量。
   - `docs/manual/`：經決議且已實作／驗證的模組行為、資料/API 契約。
   - `docs/overview/`：供導覽的摘要，連回權威規格，不自行定義第二份規格。
   - `FUTURE_IMPROVEMENTS.md`：尚未核准或尚未完成的候選工作。
   - `CHANGELOG.md`：已完成變更及其驗收證據。
   - `docs/references/Copilot_Review.md`：審查建議；除非已被總待辦採納，否則不視為已決議工作。

### P1 — 把規格、現況、提案與證據分開

1. **給每個章節標示狀態與依據**：使用一致標籤，例如「現行已驗證」、「已決議待實作」、「候選提案」、「歷史／已除役」。現況項目記錄核對日期、程式碼／資料／測試連結；提案則不可使用「目前系統支援」等完成式措辭。
2. **避免把易變測量值寫成永久規格**：測試總數、檔案大小、FPS、網路節省比例、節點數、記憶體改善百分比等應記錄測量環境、方法、日期與來源。沒有實測資料時，改列「待驗證目標」，不要承諾「永遠 60 FPS」、「零資料遺失」或特定百分比。
3. **為介面與操作規則建立一份鍵位表**：目前文件對 `I`／`L` 探查或撤離、`M` 地圖、`Esc` 退出／關閉、`WASD` 轉向與移動等描述不一致。指定一份權威鍵位表，逐項定義作用場景、焦點條件、快捷鍵衝突與可重新綁定規則，再由 QUICKSTART、FE 手冊及佈局指南引用。
4. **建立共用詞彙與模型字典**：統一五維屬性代碼、資源名稱、DamageType／元素分類、Buff 分類、裝備槽位、狀態名稱與方向命名。對「元素數量」及元素代碼的描述尤其需要釐清：M3 稱「九大傷害類型」，但列出的物理、五行、風及陰陽種類多於九項；M3-1 又列入雷、冰、毒等類別。應分清「傷害型別」、「元素家族」、「狀態標籤」和別名，避免手冊彼此推導出不同模型。
5. **整理版本與模組術語**：文件交替使用「六大前端模組」、「七大視圖區塊」及「七層 CSS」；這三者可同時成立，但應明確定義「模組、畫面區塊、樣式層」不是同一計數。FE-6 與 UI 規劃也分別出現七層與六個連續樣式模組的敘述，需以實際載入順序統一。另應核對 SaveData schemaVersion（手冊描述 v2，歷史待辦仍保留 v1 遷移語句）及 Java／Spring 版本陳述。

### P1 — 將長期遊戲構想改造成可驗收的現代規劃

1. **先定義目標體驗與垂直切片**：以「城鎮整備 → 地牢探索 → 戰鬥抉擇 → 戰利品／成長 → 安全撤離／存檔」為核心閉環，為每階段列玩家目標、決策、失敗代價、所需 UI 回饋及完成條件。先完成一段高品質可玩內容，再擴充地圖、系統或內容量。
2. **用玩家結果而非技術名詞排序功能**：對晝夜事件、SAN 異化、天候、裝備詞綴、Gamepad、多人合作等候選功能，描述要改善的玩家問題、目標族群、依賴、製作成本、風險、驗證方法及退出條件。以小型原型／玩家測試驗證核心樂趣後再擴大。
3. **區分近期單機範圍與遠期多人目標**：架構願景中的萬人併發、分散式 Actor、Redis／gRPC、跨服和雲端同步，與目前單機優先、模組化單體的階段不同。把它們標為遠期探索，不先引入其複雜度；只有在明確多人需求、容量測試和營運條件成立後，才做架構決策。
4. **為玩法設計使用短版功能提案**：每個大型玩法先說明玩家對象、核心循環中的位置、玩家可做的選擇、反制／失敗與復原、獎勵成本、所需視覺回饋、可調參數及非目標，避免先堆技術清單再倒推玩法。
5. **讓每項玩法提案有可測量驗收**：例如戰鬥機制以「玩家是否看懂敵人意圖、能否選擇可行反制、失敗是否可歸因」驗證；探索以「迷路原因、回程壓力、資訊可見性」驗證。用原型或玩家測試訂出基線與目標，避免只以「更沉浸」、「更刺激」或理論效能數字作為 DoD。
6. **把無障礙、減少動態效果與弱網行為列為需求**：在互動提案階段就涵蓋鍵盤／手把映射、焦點與螢幕閱讀器語意、色彩對比、`prefers-reduced-motion`、行動裝置觸控目標、斷線後狀態恢復，以及是否重送指令的明確規則，而非只留在未來清單。

### P1 — 精簡重複藍圖並改善工作效率

1. **將長期候選項目集中於 `FUTURE_IMPROVEMENTS.md`**：目前多本 FE／M 手冊均有四至五大「未來架構演進」章節，與中央 P0～P3 路線重複，容易產生多個狀態來源。模組手冊保留已決議的現況及短小的相關待辦連結；完整候選項只維護在中央總表。
2. **每項工作使用一致紀錄格式**：至少包含唯一 ID、現況證據、玩家／工程問題、優先級、前置依賴、範圍與非目標、驗收條件、測試或量測方法、風險及狀態。標記完成時連結對應 PR／變更紀錄／測試證據；「完成」不可只代表文字已寫或程式已編譯。
3. **維持 `ACTIVE_TASKS.md` 精簡、可執行**：一個當前任務只放真正要執行的工作，拆分時以可獨立驗收的垂直切片為單位。每個步驟寫明輸入、產出、邊界案例及測試；不要在任務卡內重複貼完整模組規格。

### P2 — 建立低成本文件品質防線

- 在 CI 或本機驗證加入 Markdown 相對連結檢查、重複／遺失章節錨點檢查，以及已知過期路徑檢查。
- 對 JSON 範例使用實際 Schema／反序列化驗證；對 DTO、枚舉、快捷鍵及 CSS 載入清單，優先從程式碼／資料產生文件表格，或用測試驗證人工文件仍相符。
- 對「已完成」、「目前」、「最新」、「全數」等易過期語句定期檢查；不要把本機絕對 `file:///` 路徑當作跨平台文件連結。
- 文件更新範圍依變更類型選擇，不要求每次改動都重讀所有手冊；由目錄索引、檔案連結及維護責任人指引相關閱讀。

## 五、建議落地順序

1. **先修索引**：確認 17 個失效連結的正確目的，替換或移除失效審查引用。
2. **核定權威來源與術語**：確認文件責任分界、玩法與技術詞彙表，並標記已實作／提案／歷史狀態。
3. **對照程式與資料修正文案**：優先校正鍵位、週期、DamageType／元素分類、schemaVersion、CSS 層級及模組路徑。
4. **收斂重複 roadmap**：保留中央總待辦中的完整候選規劃；各模組手冊改為短連結。
5. **補文件 CI 防線**：先導入相對連結與範例格式檢查，再逐步增加 JSON／契約同步測試。
6. **以垂直切片驗證玩法**：在擴張大型系統前，以實際可玩流程和玩家測試確認核心體驗，再依證據升級優先級。

## 六、後續維護原則

- 本次建議尚未代表所有遊戲設計已被核准；實作前由使用者／專案負責人決定範圍與優先級。
- 被採納的候選項移入 `docs/plans/FUTURE_IMPROVEMENTS.md`；啟動中的工作再拆入 `ACTIVE_TASKS.md`。
- 只有已從程式碼、資料及測試核對的內容，才更新為現況規格；已完成項目以測試或變更紀錄佐證。
- 每次只更新相關權威文件及必要索引，避免把同一數值複製到所有概覽、手冊與規劃稿。
