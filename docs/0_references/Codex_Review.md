# 前端任務清單 Review 報告

**範圍：**`docs/3_task_lists/frontend` 下 FE1–FE6 六份文件，並抽查各自對應的 L2 規格、HTML、JavaScript 與 CSS。  
**結論：**六份文件的模組索引與大致分工清楚，多數已完成項目有相應程式資產；但目前不宜直接把完成百分比當成可驗收的進度。主要問題是個別項目的描述超出實際前端職責、文件引用過時，以及部分待辦和現行 L2 規格可能互相衝突。

## 優先修正

1. **FE1 的終端元素 ID 寫錯。** 任務寫終端為 `#dev-console`，但目前 HTML 的實際 ID 是 `dev-console-modal`，輸入框則是 `dev-cmd-input`。請修正 `docs/3_task_lists/frontend/FE1_CORE_STATE_TASKS.md` 第 26 行及相關引用。這是明確的文件與程式不一致。

2. **FE4-4 可能提出與現行版面規格不同的方向。** 待辦提議手機底部五分頁與 PC 三欄版面；但 `docs/2_specifications/frontend/FE4_TOWN_HUB_AND_ACTION_BAR.md` 第四節定義的是桌面雙主區、窄版垂直單欄。任務雖標為長線藍圖，仍應標明這是待決策的規格變更，並釐清要沿用或取代目前版面，再建立實作驗收條件。參見 `docs/3_task_lists/frontend/FE4_TOWN_HUB_TASKS.md` 第 36–38 行。

3. **FE5-2 的「12Hz 閃爍」驗收條件需要重新定義。** 12Hz 是明確的高頻閃爍要求，且 `docs/2_specifications/frontend/FE6_CSS_TOKENS_AND_THEMES.md` 要求支援減弱動效。建議改用低頻光暈或短暫翻牌亮光，並把 `prefers-reduced-motion` 行為納入驗收。參見 `docs/3_task_lists/frontend/FE5_PARTY_EQUIPMENT_TASKS.md` 第 46–48 行。

4. **FE2 已完成項目的措辭容易讓人以為畫布透視已完成。** FE2 任務把「前方景深文字與透視」「射線阻擋遮擋」列為完成，但 L2 清楚說現行功能是 2D 迷霧雷達與前方文字探查卡，圖像透視畫布仍是藍圖；目前 `src/main/resources/static/js/panels/dungeon-panel.js` 主要渲染雷達與後端提供的前方文字。建議把完成項改寫為「呈現後端前方探查結果與已知地塊」，將畫布透視保留為待辦。參見 `docs/3_task_lists/frontend/FE2_DRPG_VIEWPORT_TASKS.md` 第 20 行起及 `docs/2_specifications/frontend/FE2_DRPG_VIEWPORT_RENDERER.md` 第 28–36 行。

## 跨文件共通問題

- **完成度沒有計算依據。** FE1 90%、FE2 90%、FE3 95% 等數字未連到任務權重或驗收狀態。建議改成「已完成／進行中／待決策／待實作」，或附上計算方式。
- **已完成項目缺少驗收證據。** 文件列了成果，但多數沒有連結對應程式位置、測試或手動驗收紀錄。建議每項完成任務附至少一個證據連結；不要只在描述中寫「已完成」。
- **驗收語句常是主觀形容。** 像「流暢」「無卡頓」「視覺爽快感倍增」難以穩定驗收。建議改成裝置／視窗範圍、互動步驟、預期結果和必要的效能或可及性行為。
- **待辦狀態混用。** 六份文件同時使用 `[ ]`、P 等級、「已決議待實作」和「長線演進藍圖」，但未定義它們的優先級關係。建議統一狀態欄位，並把待規格決策的事項與可直接實作的待辦分開標示。
- **本次未執行測試或瀏覽器驗收。** 報告依文件與靜態資產核對；交互流程、視覺效果和效能仍需另行驗收。

## 建議處理順序

先修正 FE1 ID、澄清 FE2「射線／透視」完成範圍、決定 FE4-4 的規格方向，並改寫 FE5-2 的閃爍要求；之後再統一六份清單的狀態、完成度依據與驗收證據格式。
