## 已確認差異與建議

### 1. M8 完成度看板不一致（低風險、明確差異）

`docs/3_task_lists/README.md` 的 M8 列標示 **95%**，但 `docs/3_task_lists/backend/M8_SAVE_AND_PERSISTENCE_TASKS.md` 標示 **100%**，其列出的六項任務均已完成，沒有未勾選待辦。

**建議：**確認 M8 是否仍有未列出的 5% 工作。若沒有，將總覽改為 100%；若仍有範圍外工作，請在 M8 任務清單加上明確待辦與驗收條件，避免總覽數字沒有依據。

### 2. 字級最低 13px 的完成狀態與程式不一致（中風險）

`docs/3_task_lists/FUTURE_IMPROVEMENTS.md` 的 UI-01 將「字級 ≥13px」標示為已完成（第 67 行）。但 `docs/3_task_lists/frontend/FE6_CSS_TOKENS_TASKS.md` 說明只有全域 Token `--font-xs: 13px` 已建立，9–12px 的歷史角標仍待漸進收斂；目前 `style-01-tokens-and-shell.css` 可見 12px 宣告，`style-02-combat-arena.css` 可見 11px 與 12px 宣告。

**建議：**把 UI-01 的完成描述限縮為「建立 13px 全域基準 Token」，或把所有生效文字至少 13px 設為未完成工作，並連結 FE6 後續任務。若小型裝飾數字有例外，也應寫明例外範圍，避免「全域最低字級」和實際 CSS 相矛盾。

### 3. 完成百分比缺少可追溯的計算規則（治理性問題）

多份模組清單使用 85%、90%、95% 等完成度，但文件沒有提供任務權重、計算方式或這些百分比涵蓋的範圍。M8 的 95%／100% 差異是此問題的具體例子。

**建議：**以「已完成／進行中／待決策／待實作」作為主要狀態；若保留百分比，請為每個模組定義工作項與權重，並讓總覽直接引用模組清單中的單一數值來源。

### 4. 未來改善總表與模組任務清單需維持單一狀態來源

`README.md`、各模組任務文件及 `FUTURE_IMPROVEMENTS.md` 都記錄進度，容易出現同一需求在不同清單有不同狀態或完成範圍。UI-01 的字級例子已顯示這種漂移；M8 進度也有同類狀況。

**建議：**在總表引用任務 ID 或模組清單狀態，不重複手動維護描述與完成百分比；對跨模組事項指定一份主清單，其餘只保留連結。

### 5. M5-5 應區分已存在的解算能力與仍待實作的擴充範圍

`M5_SKILL_AND_PROGRESSION_TASKS.md` 將小隊動態終結技解算器列為待辦，並要求新增 `DynamicComboResolverTest`。目前程式已有 `ComboResolver.executeFormationFinisher`、`FormationFinisherClassifier`，並有 `CrossComboAndFormationResonanceTest`、`FormationFinisherClassifierTest` 等測試。因此「解算器從無到有」可能不是準確的待辦描述；未完成範圍看起來更可能是更廣的 16 雙星、8 三才、4 樹領域與 15 種隊伍構成覆蓋。

**建議：**把已有能力列為現況，將 M5-5 限定為尚缺的組合種類、領域規則、插槽互動或資料化範圍；驗收時可擴充現有測試，除非新測試類別本身有明確價值。
