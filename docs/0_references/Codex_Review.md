# 文件對齊審查報告

## 結論

**三層文件尚未完全對齊，建議先修正高優先級問題，再將此文件組合作為可追蹤的完整規範鏈。** 目前模組骨架大致相符：4 份需求文件對應 10 份後端規格（含 M3.1）、6 份前端規格及 3 份 Schema；對應的任務清單也都存在。但「檔案存在／有模組對照」不等同於需求內容完整映射或規格項目完整拆成任務。缺少穩定需求 ID 與逐項追溯矩陣，使完整性目前無法可靠地宣稱或衡量。

## 主要發現

### P1 — Level 3 看板存在已失效的名稱、測試與狀態資訊

`docs/3_task_lists/README.md` 的模組矩陣連結文字仍使用舊文件名，例如 `M1_TOWN_HUB.md`、`M3_1_BUFF_STATUS.md`、`M4_PARTY_FORMATION.md`、`M9_STATE_PIPELINE.md` 等，實際規格檔名則是 `*_AND_*` 或 `*_AND_EVENTS.md`。目前連結目標多數正確，但可見標籤會誤導讀者。矩陣的測試名稱 `PartyInventoryAndMadnessTest` 亦與已除役的「道心崩潰／魔化」概念衝突，其他測試名及百分比也沒有此文件中的計算依據。建議統一顯示實際檔名，移除或更新過時測試名稱，並為完成度定義一致的計算規則或標示為估計值。

### P1 — M9 任務清單將規格已要求的動作協定列為未完成重構

`docs/2_specifications/backend/M9_STATE_PIPELINE_AND_EVENTS.md` 第三節已規定前端請求使用結構化 JSON，並列出 `MOVE`、`CAST_SKILL`、`FORMATION_FINISHER`、`TOWN_FACILITY`、`EQUIP` 等協定範例；模組定位也明確要求除役文字 MUD 命令解析器。相對地，`docs/3_task_lists/backend/M9_STATE_PIPELINE_TASKS.md` 將「所有互動 100% 收斂為 JSON」列為待辦，還以 `TOWN_FACILITY` 規格未出現的 `INTERACT_FACILITY`、`REST_PARTY` 作為目標動作。這使規格的既定契約和任務狀態／命名不一致。應以實際程式現況判定哪些 action 已實作，再將待辦限縮到差異；統一兩份文件的動作名稱與 payload 契約，並明確列出規格中尚未描述的加點等動作。

### P1 — MUD／房間拓撲除役要求未徹底落實到下游文件

`docs/1_requirements/GAMEPLAY_CORE_LOOPS.md` 第五節明確要求零 MUD 指令，第一節也裁定除役 MUD 及 SAN 崩潰魔化玩法；`UI_UX_REQUIREMENTS.md` 同樣要求移除文字命令輸入與房間移動。雖然 M9 規格已描述除役方向，仍有多處下游保留衝突表述：

- `docs/3_task_lists/backend/M1_TOWN_HUB_TASKS.md` 的已完成項目仍稱 `Room.broadcast(String message)` 為單機通道，且待辦以舊 `RoomService.exits` 拓撲作為系統遷移目標。
- `docs/3_task_lists/backend/M9_STATE_PIPELINE_TASKS.md` 的已完成項目仍提及「房間唯一主角引用」及「多人廣播遍歷通道」。
- `docs/3_task_lists/frontend/FE2_DRPG_VIEWPORT_TASKS.md` 職責仍寫「八方步進羅盤」；需求規格描述的是地牢走步控制，不應因此延伸出營地房間移動。
- `docs/3_task_lists/README.md` 仍列出 `PartyInventoryAndMadnessTest`。

應清理或標記這些為歷史遷移紀錄，並避免讓已除役概念留在目前狀態與驗收描述中。若 SAN 作為精神護盾數值仍保留，須與已除役的 SAN 歸零魔化機制清楚區分。

### P1 — 需求至規格沒有逐項追溯，無法證明 Level 2 涵蓋全部 Level 1

`GAMEPLAY_CORE_LOOPS.md` 對五大支柱及核心循環已有模組提示，但整體需求未使用可追蹤 ID，也沒有一份矩陣逐項列出每條需求由哪些規格章節承接、落在哪些任務清單。`MODULES_MAP.md` 是模組職責地圖，不足以證明所有需求均已分配。尤其世界觀、序章敘事、16 項技能概念、PC／手機版 UI、文字日誌、出征撤離規則等跨模組需求，沒有可直接檢查的完整映射。建議為需求建立穩定 ID，增加 Requirements → Specification section → Task ID 三向矩陣，並標出「不適用」及其理由，而非只靠模組名稱推定涵蓋。

### P1 — Level 3 任務清單尚未達到「規格完整實作項目清單」的可追蹤程度

各模組清單普遍採少數概括的已完成項目加少數未來待辦；它們適合做進度摘要，但不足以確認每一項規格要求都有對應的實作、驗收與狀態。例如：

- `M1_TOWN_HUB_AND_FACILITIES.md` 詳列五種設施各自的分解、強化、詞綴重鑄、晶片調試／插槽、技能樹、補給、基因強化、區域／難度選擇，以及 NPC 對話、任務與好感度；`M1_TOWN_HUB_TASKS.md` 僅列資料化、休整、服務／事件派發等概括項目，未逐項確認上述行為的狀態與驗收條件。
- `M9_STATE_PIPELINE_AND_EVENTS.md` 描述多種 action、單一狀態 DTO、事件與時間線；M9 清單只有少量合併項目，且如上所述其 action 待辦與規格重複／命名不同。
- `UI_UX_REQUIREMENTS.md` 的手機直向版面、PC 三欄配置與可操作性要求，未見由總覽建立的需求對應表以確認各 FE 規格與任務已涵蓋所有視口／場景。

建議把規格中的每個可交付行為拆成具唯一 ID 的任務項目，標記未開始／進行中／完成／除役，附驗收條件與規格章節連結；完成項目應有可核對的實作證據，不能只以模組完成百分比代表覆蓋完整。

### P2 — 多存檔槽位的規範與任務範圍需裁決一致

`GAMEPLAY_CORE_LOOPS.md` 第五節寫「單存檔單主角」；`UI_UX_REQUIREMENTS.md` 要求本地存檔管理；M8 規格與 `MODULES_MAP.md` 則描述 `slot_*`、五個手動槽位及自動槽位；M8 任務待辦又寫前端 Slot 1~3。應釐清需求的「單存檔」是單一遊戲狀態／主角，還是單一槽位，再讓規格與任務使用一致的槽位數量與語意。

### P2 — 進度看板中的完成度、測試基準與任務狀態未具足夠證據

`docs/3_task_lists/README.md` 宣稱全專案「376+ 項測試 100% 綠燈」，各模組列百分比及關鍵測試；但清單沒有定義完成度分母，也沒有指向本次執行結果。模組任務項目以 `[x]` 標完成，也未普遍連到可核實的程式碼／驗收證據。此報告未執行測試，因此不判定這些主張真偽；建議把「文件進度」與「測試執行狀態」分開記錄，附執行日期、命令與結果來源，且完成狀態連結驗收證據。

## 建議修正順序

1. 先依 Level 1 裁決單存檔與多槽位、SAN 存續範圍、設施／營地互動及 action 名稱等歧義；清除目前文件內互相矛盾的現行描述。
2. 建立 Level 1 需求 ID 與需求—規格章節—任務 ID 追溯矩陣，逐項確認所有需求都有規格承接。
3. 依規格拆解每個模組的完整實作項目及驗收條件，將已有項目映射至新 ID，補足漏項並更新進度證據。
4. 更新 `docs/3_task_lists/README.md` 的實際檔名、測試名稱、完成度定義及測試基準來源；核對所有相對連結。
5. 在文件變更流程中要求：L1 變更必須檢查 L2 追溯列；L2 變更必須檢查 L3 對應任務；未同步前不得宣稱對齊完成。
