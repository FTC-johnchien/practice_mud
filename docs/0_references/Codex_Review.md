# 《深淵仙途》文件規劃審查與改進建議

> 審查範圍：`docs/` 下全部 Markdown 文件，排除 `0_archive/` 與 `0_references/`。共盤點 73 份文件，涵蓋需求、後端與前端規格、資料 schema、技能樹、實作任務和進行中工作。
>
> 本文件是審查建議，不是已核准的遊戲規則或實作規格。文中引用的是審查時可見的文件狀態；落地前應先核對程式、資料和最新裁決。

## 總評

文件體系已具備良好基礎：需求、模組規格、模組任務、當前迭代分層清楚；`docs/3_task_lists/README.md` 有需求到模組、任務和測試的追蹤矩陣；戰鬥、地牢、存檔和資料契約也已按領域拆分。這些內容足以支援單機 DRPG 的持續開發。

目前最大的風險不是缺少更多設計點子，而是文件數量與重複規則增加後，權威來源、狀態和依賴關係難以維持一致。建議先消除互相矛盾的決策和過期狀態，再把遊戲規劃從「功能清單」補成「玩家體驗、內容節奏、驗收證據」的閉環。暫時不建議再擴張大量高階機制或以抽象效能目標驅動架構。

## 優先處理的文件風險

### P0：清理已互相衝突的設計裁決

- `docs/1_requirements/GAMEPLAY_CORE_LOOPS.md` 宣告除役 SAN／精神崩潰一類的負面機制，但 `docs/3_task_lists/README.md` 的 R9 仍將 SAN 護盾和「精神萎靡」列為需求，並連到 M1、M2、M3.1 與測試；`docs/2_specifications/MODULES_MAP.md` 也仍描述 SAN 護盾。這會使實作者無法判斷是保留、簡化還是完全移除。
- 「單一真相源」與「不在低層重抄規則」是明確原則，但 85/15、SAN、模組完成度、測試數量、技能數值及待實作決策仍在多份文件重述。現況與原則不一致，修改一次往往需要猜測同步範圍。
- `docs/4_active_tasks/ACTIVE_TASKS.md`、`SPRINT_GOAL.md`、`docs/3_task_lists/README.md` 各自描述焦點、里程碑、完成度和測試數；例如不同段落出現 376+、388、395 等測試基準。未標日期的數字無法作為可靠現況。

**建議做法：**建立一頁「設計裁決紀錄」，每筆決策包含 ID、狀態（提案／已決議／已除役）、日期、裁決內容、受影響文件和替代方案。決策正文只在該頁保存；需求文件只保留玩家體驗目標，模組文件引用裁決 ID。針對 SAN 做一次明確結案：保留哪些可見效果、刪除哪些規則、舊測試與欄位如何處理，再同步追蹤矩陣與任務清單。

### P1：讓追蹤矩陣可驗證，而非只表示「有對應」

`docs/3_task_lists/README.md` 的追蹤矩陣是很好的起點，但目前混合了需求來源、規格章節、任務、測試、完成百分比和真值路徑；部分狀態在表格中只是人工宣稱。例如「100% 完備」「95%」和全域測試綠燈若沒有日期、命令或 CI 連結，無法確認仍有效。文件亦聲稱 L2 與 L3 一對一鏡像，但前端 GUIDE/PAGE 等規格採多對一任務對應，技能樹由共用任務承接，實際上不是嚴格 1:1。

**建議做法：**把「追蹤關係」和「即時狀態」分開。每項需求使用穩定 ID（如 `REQ-COMBAT-001`），連到規格章節、驗收情境、任務 ID 及自動化檢查。完成度改為明確狀態（未規劃／規劃中／實作中／驗收中／完成／除役），只有能定義分母時才使用百分比。測試和連結檢查應記錄最近一次執行日期、命令及結果；若能由 CI 產生，就不要手動維護數字。修正文案中的「1:1」為實際支援的一對多／多對一追蹤模型。

### P1：分清「需求、已決議、提案、未來想法」

`CYBERPUNK_CULTIVATION_SPEC.md` 同時包含世界設定、17 技能樹全覽、大量合擊組合與長線 backlog；多份模組規格在核心契約後加入「現代化／未來擴充」章節，其中有尚未決定的機制、精確公式和效能方向。像 `【已決議待實作】`、`Future Roadmap`、現行規格並列時，讀者難以判斷哪些內容可以直接實作。需求層文件也含有技能階級、百分比、明確數值與欄位名，和 `docs/README.md` 所訂「需求層不放程式 ID、JSON 欄位與戰鬥平衡數值」的界線不一致。

**建議做法：**每份規格開頭加入短小狀態欄：文件負責範圍、狀態、版本／更新日期、權威資料來源。內容採一致分區：已核准規則、待裁決問題、未承諾的候選方向。未核准的數值與新機制不得放在規範性正文；移至提案或 backlog，並標明尚未評估。將技能樹願景、可執行技能資料契約和組合技清單分開，避免一份文件兼任三種用途。

### P1：降低文件治理本身的摩擦

`docs/README.md` 對 L1→L2、L2→L3 的每次變更都要求檢查下游並由使用者決定是否修改；`DOCS_ALIGNMENT_MASTER_PLAN.md` 和 `DOCS_ALIGNMENT_ACTIVE_TASKS.md` 又規定多階段簽核、模型角色和逐步操作。這種治理對大範圍裁決有幫助，但若用於每個小修訂，會讓文件流程比功能交付更重，並使任務依賴特定 AI 或手動簽核狀態。現有連結腳本只檢查連結存在，不能證明規格、程式和資料一致。

**建議做法：**採風險分級變更：影響玩家規則、存檔格式、平衡或模組契約的變更才要求完整下游影響分析；拼字、排版和不改語意的整理只需一般檢查。把「使用者確認遊戲設計裁決」與「是否需要更新文件」分開。將長期可重用的自動檢查放在腳本／CI，對齊任務卡只描述一次性遷移工作，完成後封存，避免它成為永久流程手冊。

## 讓規劃更符合現代單機遊戲開發

### 1. 以玩家體驗和可玩的切片排序，而不是以模組覆蓋率排序

目前五大支柱、模組清單和 VS-01 序幕方向已提供產品定位，但活躍任務偏向「要加哪些資料、技能、UI」和技術驗收。建議每個章節／垂直切片先定義一段可玩的玩家旅程：進入營地、選擇遠征、探索、遭遇戰、取得戰利品、撤離、整理 Build。每個步驟說明玩家目標、選擇、回饋、失敗或中斷時的處理，以及完成後解鎖什麼。

每個切片設定少量可觀察的驗收指標，例如完成一輪遠征所需時間、遭遇戰是否能辨認敵方蓄力並做出反應、掉落是否造成有意義的裝備選擇、首次失敗後能否理解損失並願意再試。這些是內部設計驗收目標，不等同於量產後遙測 KPI；單機專案可以用可重現的人工走查和測試存檔驗證。

### 2. 先確立內容節奏與可重複遊玩的理由

文件中已有長線地牢、Boss、裝備、難度詞綴、17 技能樹與合擊構想，但尚需一個共同的內容節奏模型，說明各層探索時間、戰鬥密度、休整點、Boss 間距、掉落節點、解鎖節奏，以及新手到終局的成長曲線。建議以第一章垂直切片校準基準，再定義地城樓層範本、遭遇類型、精英／首領功能、獎勵預算和章節節點；不要先承諾大量技能與合擊數量，再回頭尋找容納它們的遊玩時間。

對刷寶迴圈，補上掉落的用途與決策：新裝備如何改變 Build、重複物品如何處理、低稀有裝是否仍有拆解價值、玩家何時需要回營地，以及失敗是否造成過度挫折。將「85/15」視為敘事侵入程度的設計方向，不要把它當成可直接量測或要求每份文件引用的精確比例。

### 3. 讓平衡資料可追溯、可比較、可回歸

精確數值散落在技能樹、戰鬥規格、Buff 文件、schema 範例和任務描述。建議建立明確的平衡資料來源，記錄每個數值的單位、範圍、計算順序、適用對象、例外及版本。為傷害、抗性、Poise、控制效果、冷卻／資源和掉落率準備代表性戰鬥情境，讓改值前後能比較擊殺回合、玩家存活率、資源消耗和 Build 差異。

優先以表格或可解析資料表保存大量可調數值，規格文件描述規則和設計意圖。若新增資料驅動能力，連同驗證器、預設值、錯誤訊息和舊資料遷移一起規劃；「100% 資料驅動」不應要求把所有邏輯都塞進 JSON，也不應把每一種未來可能性抽象成通用擴充框架。

### 4. 把單機存檔和離線可靠性列為核心玩家體驗

M8 已涵蓋多槽、版本和備份方向，建議補全玩家可理解的存檔契約：何時自動／手動存檔、地城中斷或程式崩潰後恢復到哪裡、損壞存檔如何選擇備份、不同版本如何升級、未知或缺漏欄位如何處理、玩家如何複製或匯出存檔。對單機作品，存檔遺失和更新破壞舊存檔會直接損害信任，優先度通常高於假設性的高並發或無鎖效能目標。

每個存檔版本應有遷移策略和最小兼容測試資料；寫檔採安全替換／備份流程，並記錄可診斷錯誤。地城不可任意存檔是遊戲規則，仍需另行定義斷電、當機、更新與退出時的恢復行為，避免把「禁止存檔」誤解為可以丟失玩家進度。

### 5. 把可擴充性建立在清楚的內容契約上

遊戲目前定位為純單機單體，文件又提到模組化、資料驅動和可能的 modding。建議明確界定近期要支援的是內部策劃內容、可熱載入資料、玩家自訂內容，還是正式模組；各自的驗證、相容性和安全需求不同。近期先確保技能、物品、敵人和地城資料使用穩定 ID、schema 版本、引用完整性檢查、可理解的驗證錯誤和可預期預設值。等內容量或玩家需求證明必要時，再定義公開 mod API。

擴充點應由至少兩個真實使用案例支撐，並有版本治理和錯誤隔離。不要為了「未來可能支援」過早增加外掛執行環境、泛型事件框架或複雜相容層。

### 6. 將 UI／可及性需求納入規格和驗收

`UI_UX_REQUIREMENTS.md` 已指出 PC 優先、手機直向與主要佈局方向，但部分被標為待深入討論。建議先明確目前交付平台和輸入方式，再把可用性需求落到 FE 規格：鍵盤操作、焦點順序、文字縮放、色彩對比、狀態不能只靠顏色表達、動態／閃光效果減弱、動畫可簡化、音效與字幕控制、窄螢幕降級行為。對半即時戰鬥，還要定義暫停／減速、戰鬥速度和特效密度如何支援不同玩家。

以 UI 狀態矩陣驗收主要畫面：載入中、空資料、錯誤、資源不足、戰鬥進行中、玩家受控、首領蓄力、勝利／失敗、存檔衝突。這能比單張靜態佈局圖更有效地防止前後端邊界漏接。

## 建議的文件結構與維護方式

建議保留現有四層主結構，收斂每層的責任：

| 層級 | 應回答的問題 | 建議保留的內容 | 不宜承載的內容 |
|---|---|---|---|
| 需求 | 玩家要感受到什麼、成功條件是什麼？ | 支柱、玩家旅程、平台／範圍、體驗原則、需求 ID | Java 類別、JSON 欄位、未核准公式、逐任務追蹤 |
| 規格 | 系統行為與邊界如何定義？ | 模組責任、輸入輸出、狀態轉移、失敗行為、資料契約、例外 | 未決提案混入正式規則、複製整份任務狀態 |
| 任務 | 要交付什麼、如何驗收？ | 小而可完成的工作、依賴、驗收條件、證據連結 | 重複規格正文、無日期完成百分比 |
| 當前迭代 | 現在做什麼、阻塞在哪？ | 當前目標、負責任務、風險、完成證據 | 長期架構藍圖、另一份全域進度總表 |

每份規範性文件建議採相同的輕量前置資訊：`文件狀態`、`最後核對日期`、`權威來源／被引用 ID`、`適用版本`。加上以下文件檢查：連結有效、需求 ID 存在、任務 ID 唯一、schema 範例能驗證、正式文件沒有未標記提案、除役項目仍被追蹤矩陣引用時發出警告。CI 只需對實際重要的規則設防，不要把文件檢查變成另一套需要手動維護的大型治理系統。

此外，`docs/README.md` 目前描述審查報告位於 `docs/0_references/`，而本報告依指定寫在 `docs/references/`。請後續決定要把此目錄正式納入參考文件地圖、或調整目標路徑與導覽說明，避免位置與治理規則不一致。本次遵照指定路徑建立報告，沒有改動其他文件。

## 建議執行順序

1. **先結清裁決衝突：**定案 SAN／精神萎靡的存廢與影響範圍；標記所有未決數值、技能與未來擴充為提案或待裁決。
2. **建立可追蹤的需求與決策索引：**為核心玩家體驗和系統需求配置穩定 ID；修正 L2/L3「1:1」與實際關係不符的描述。
3. **以 VS-01 補足遊戲閉環驗收：**定義一輪遠征、戰鬥回饋、掉落選擇、撤離／失敗和存檔恢復的可玩驗收情境。
4. **收斂狀態與證據來源：**指定唯一當前看板；完成度、測試數、連結數只在可自動產生或帶日期證據時發布。
5. **完善資料與存檔生命週期：**補穩定 ID、schema 版本、資料驗證與存檔遷移／備份／恢復契約。
6. **最後再擴充長線系統：**依垂直切片驗證結果排序技能樹、合體技、地城詞綴、公開 modding 和進階效能工作。

## 審查結論

文件已經有清楚的產品方向、廣泛的系統規格與可用的追蹤骨架；下一階段最能提升穩定性與效率的工作，是縮減重複真相、把裁決狀態說清楚、讓完成宣稱附帶證據，並以可遊玩的章節切片驗證規劃。這會同時降低文件漂移風險，並讓擴充內容有明確的體驗、平衡、存檔與驗收依據。
