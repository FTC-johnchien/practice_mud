# Copilot 設計建議：DQ / FF 功能選單

> **狀態**：設計提案，尚未實作
> **日期**：2026-09-27
> **範圍**：將現有「狀態」入口重整為「選單」，承載道具、裝備、技能、角色、隊伍、陣法、戰術方針與存讀檔。

> **本次更新**：補充探索／戰鬥／選單的共同布局、隊伍 HUD 與 footer bar 重構，以及 HP / MP / SP / SAN 的一致顯示規格。

## 結論

建議採用單一固定外框的階層式功能選單：左側切換主要功能，右側顯示該功能的頁籤、列表或管理畫面。保留 DQ / FF 的清楚分類與逐層深入感，同時沿用目前遊戲的 WoW 快捷列、隊伍狀態與指令操作。不要讓每個主功能都再開一個互相堆疊的 modal；唯有裝備選擇使用選單內的子視圖，完成後回到原裝備位置。

這是 UI 與互動重整，不應順帶重寫物品、技能、陣法或存檔領域模型。現有 `party-modal.js` 已涵蓋隊員、裝備、技能書、Gambit 與戰陣盤；背包和存檔也各有既有操作流程，應先抽換導航與版面，再逐步補齊缺少的比較資料和隊伍排序能力。

## 0. 本次 UI 重構決策

### 0.1 先定義三種資訊密度

目前破版的根本原因不是單一字級太小，而是探索、戰鬥、隊伍狀態和操作按鈕同時搶同一個固定高度。建議把畫面拆成三種密度，所有頁面共用同一個 shell，但不共用同一套卡片尺寸：

- **探索密度**：閱讀地圖、方向、房間描述與環境互動；正文和關鍵狀態至少 13px，地圖格子使用固定尺寸，內容區可捲動。
- **戰鬥密度**：閱讀敵我狀態並選擇目標／技能；以「目標區、隊伍摘要、所選角色技能台」三層分區，不把完整角色資料塞進戰鬥卡片。
- **管理密度**：選單中的角色、裝備、技能、陣法與存讀檔；允許較多欄位，但內容視口獨立捲動，外框尺寸不隨列表改變。

不要用全域縮小字體來容納內容。以 `13px` 作為探索與戰鬥的最低可讀字級，次要提示可以降低對比度，但不要再以 10～11px 的長句作為主要資訊。若內容放不下，依序採用重新分區、折疊次要資訊、水平／垂直捲動與窄版堆疊，而不是壓縮字體。

### 0.2 共用頁面 shell

建議把現有 `.game-container` 重構為四個穩定區域：

1. **Global Header**：模式、當前區域、陣法靈威與唯一的全域選單入口。
2. **Context Viewport**：探索或戰鬥的主要內容，`min-height: 0`，內部面板各自捲動。
3. **Party Summary Rail**：固定高度的隊伍摘要，顯示每名成員的必要資源，不承擔詳細資料或完整技能盤。
4. **Context Action Bar**：只保留目前模式真正需要的動作；選單、存讀檔、陣法等管理功能不在此重複。

桌面使用 `grid-template-rows: auto minmax(0, 1fr) auto auto`；窄視窗改為上下堆疊，隊伍摘要可橫向捲動或改成單列緊湊清單。每個區域先設定 `min-width: 0`、`min-height: 0` 和明確的 `overflow`，避免 flex 子元素把整頁撐破。

### 0.3 探索頁

- 探索主視口採「地圖／前方觀察」與「環境／事件日誌」兩欄；兩欄的最小寬度與可捲動邊界固定，不讓隊伍 HUD 擠壓雷達。
- 方向鍵、換邊、視口、探查等探索專用控制放在雷達／探索區的標題列或控制列，使用固定按鈕尺寸和至少 13px 文字；不要再複製到 footer。
- 房間描述、NPC、地面物品以可折疊區塊呈現。預設先顯示區域標題、描述和可互動項目，長描述與次要提示在內容區捲動。
- 探索頁的隊伍區只作「旅程狀態列」：點擊成員可以開啟選單中的角色或技能上下文，但不在卡片內展示完整裝備、陣位孔位或技能列表。

### 0.4 戰鬥頁

- 戰鬥主視口固定為「敵方目標區 → 集火／回合狀態 → 我方成員摘要」；技能操作只在下方所選角色的 command dock 展開。
- 不以額外的大型前衛／後衛文字列佔用空間。戰鬥仍可使用後端陣法位置進行目標與傷害計算，但前端以陣法幾何位置、隊伍順序與目標高亮表達，不提供另一套前後衛設定。
- 敵方卡片保留目標、HP、控制與 Buff；我方快速列只保留編號、姓名、等級、四項核心資源、死亡／異常狀態和必要 Buff。技能消耗、CD、施法進度放入所選角色技能台。
- 戰鬥中的詳細資料使用抽屜或固定 command dock；抽屜開關不能改變主戰場高度，避免每次選角造成頁面跳動。

### 0.5 選單頁

沿用本文件既有的單一選單外框，但把它視為管理層，不再與探索／戰鬥 HUD 競爭高度。角色、裝備、技能和陣法頁可以顯示完整資料；探索與戰鬥只顯示摘要和入口。選單的內容視口獨立捲動，並在窄版將左側導覽收成水平分頁。

## 0A. 隊伍區塊與 footer bar 重構

### 0A.1 隊伍區塊歸入探索／戰鬥 shell

建議將隊伍區塊視為主要 context shell 的固定「Party Summary Rail」，不再視為獨立的頁面底部。探索和戰鬥共用資料元件，但可依模式切換排序與操作：

- 探索：隊伍摘要位於探索視口下方，成員順序就是隊伍名冊順序 `#1`～`#5`；點擊只選取角色或開啟對應選單。
- 戰鬥：隊伍摘要位於戰鬥主體下方，沿用同一順序；選中成員後才顯示技能台。
- 選單：不再重複渲染完整隊伍卡片，改由角色／隊伍頁提供完整資訊和管理動作。

每張摘要卡只顯示：`#編號`、角色姓名、`Lv.等級`、HP、MP、SP、SAN，以及會影響當前操作的少量 Buff／Debuff 或異常狀態。職業、稱號、陣法孔位、裝備、自由點數、GCD、完整 Buff 詳細文字移到選單或所選角色的詳細抽屜。文件與程式中的「6 人小隊」改為「最多 5 名隊員」，避免錯誤的固定欄數假設。

### 0A.2 移除前／後衛設定與重複顯示

- 移除隊伍摘要卡上的「前衛／中衛／後衛」badge、設定按鈕與可直接換位的 UI。
- 移除探索隊伍卡上的陣法孔位長文字；若需要提示，只顯示「陣法效果未生效」這種結果型警告，詳細原因放在陣法頁。
- 隊伍順序由 `#1`～`#5` 表示；陣法頁負責幾何配置與效果，戰鬥引擎負責實際位置與目標規則。兩者不可再由 HUD 提供第三套位置編輯。
- 戰鬥需要表達射程或目標層級時，使用戰場位置、連線、目標高亮或 tooltip；不要把「顯示前／後衛」重新做成另一組可設定狀態。
- 後端 `row`／formation slot 可以暫時保留作為規則與 DTO 相容欄位，但前端摘要 renderer 不應依它產生 badge 或設定入口。

### 0A.3 footer bar 的新職責

footer 只保留「目前模式的高頻、立即執行操作」：

- 探索：可保留文字指令輸入、開啟選單、行囊（若仍是高頻操作）與開發者終端；方向鍵、探查、休息移到探索區自己的控制列。
- 戰鬥：只顯示模式提示、撤退／集火等真正的戰鬥級操作；技能由所選角色的 command dock 提供。
- 全部移除 footer 的「存讀檔」、「陣法」、「探索」、「休息」重複入口。存讀檔與陣法只從選單進入；探索／休息不是通用 footer 操作。
- `bottom-control-panel` 不應再同時承擔 D-pad、所有模式按鈕、測試按鈕和文字輸入。開發測試按鈕應由開發者模式或終端收納，不進入玩家常駐操作列。

建議 footer 最終只是一條 48～64px 的 context action bar；沒有可用動作時隱藏或縮成狀態提示。這樣隊伍摘要能取得穩定高度，探索區也不會因重複按鈕被壓縮。

## 0B. HP / MP / SP / SAN 資源顯示契約

### 0B.1 為什麼目前只看到 HP／MP 或 SP／SAN

目前 `DrpgStateDto` 將角色的 `resourceType` 與 `currentResource`／`maxResource` 正規化成「MP 或 SP 二選一」，前端 `party-hud-panel.js` 再依 `resourceType` 只渲染一個資源欄。因此這是目前 DTO 與 renderer 的設計結果，不是角色缺少另一項能力：

- HP 和 SAN 是固定顯示。
- MP 是真元資源；SP、RAGE、COMBO、FORCE、ENERGY、STAMINA 目前被轉成同一個 `SP`／「戰氣」欄位。
- 技能資料已經有 cost type 和可用性，但 HUD 沒有把 MP 與 SP 同時作為通用核心欄位輸出。

這個正規化對早期職業摘要有用，但不符合後期所有角色都可能同時擁有法術與主動技能的設計方向，也讓玩家無法預判技能資源。

### 0B.2 建議的資料與顯示規格

將 `PartyMemberViewDto` 的顯示契約改為固定四項核心資源：

- `hp: { current, max }`
- `mp: { current, max }`
- `sp: { current, max, label, kind }`
- `san: { current, max, level }`

其中 `sp` 可以保留 `RAGE`、`COMBO` 等實際資源語義，但不應再把它誤標成 MP 的替代欄位；若角色沒有該資源，顯示 `—` 或「未啟用」，不可靜默消失。若遊戲規則要求所有角色都能使用主動技，則所有角色都必須有可計算的 SP 上限，初始值可為 0，但資料欄位仍存在。

摘要卡顯示順序固定為 `HP / MP / SP / SAN`，用四條短 bar 或兩行雙欄呈現；寬度不足時只縮短 label，不降低 13px 文字。技能詳情另外顯示實際 cost type、消耗值與不足原因，不能以「戰氣」覆蓋所有 SP／怒氣／連擊點語義。

後端應保留原始 `resourceType` 與技能 cost type，新增明確的 MP／SP 快照欄位或資源 map；前端只讀契約，不自行猜測職業。COMBO 若仍是由 SP 與連擊點共同判定，應分別回傳兩者目前值，避免 HUD 只顯示其中一個造成錯誤判斷。

## 0C. 建議實作順序與驗收

1. **資料契約先行**：補齊所有隊員的 HP／MP／SP／SAN 快照，保留資源種類與技能 cost type；新增 DTO 測試涵蓋法術職、戰技職、同時擁有 MP 與 SP 的角色，以及 SP／COMBO 的邊界值。
2. **共用 shell**：建立探索／戰鬥／選單共用的 viewport、summary rail、context action bar CSS；先讓 13px 長句在桌面與窄視窗都能捲動而不溢出。
3. **隊伍摘要 renderer**：移除前後衛 badge、陣法孔位長文與單一替代資源欄，改為 `#、姓名、Lv、HP、MP、SP、SAN、必要狀態`；保留選中成員事件，不保留位置編輯事件。
4. **footer 收斂**：移除存讀檔、陣法、方向鍵、探查、休息的重複按鈕；將方向與探查控制放回探索區，將陣法／存讀檔移入選單，將休息改為探索區的情境互動（若該場景允許）。
5. **戰鬥與選單適配**：戰鬥使用同一摘要卡但把技能操作留在 command dock；選單承擔完整角色資料、陣法位置、裝備和資源解釋。
6. **清理固定人數與舊語意**：移除「6 人」註解、六欄固定 grid 和前後衛 UI 文案；實際上限由資料決定，現行上限為 5 名。

最低驗收條件：

- 探索主資訊與控制文字不低於 13px；桌面、窄視窗、長地名、長 Buff 名稱不重疊且可捲動。
- 探索／戰鬥／選單三種模式不會同時顯示重複的存讀檔、陣法、方向、探查或休息入口。
- 隊伍摘要永遠能辨識 `#1`～`#5`、姓名、等級與 HP／MP／SP／SAN；缺少資源時顯示明確的 `—` 或「未啟用」。
- 前後衛不再是隊伍摘要或 footer 的可設定項目；陣法頁和戰鬥規則仍能正確使用後端位置資料。
- 角色有法術、戰技或雙資源時，技能台顯示正確消耗、目前值、最大值、CD 與不可用原因。
- 至少以 DTO／服務測試驗證資源契約，再以瀏覽器手動或自動檢查桌面、899px 以下窄版和 5 名隊員的布局。

## 1. 選單外框與導覽

- 將「狀態」入口及標題改為「選單」，保留原快捷鍵作相容入口，Tooltip 和快捷鍵說明同步更新。
- 左側主導覽固定為：道具、裝備、技能與法術、角色、隊伍、陣法、戰術方針、系統。右側是唯一的主要內容區，標題列顯示目前功能及必要的隊伍上下文。
- 桌面建議外框目標尺寸約 `1180 x 760`；以 `max-width: 94vw`、`max-height: 90vh` 限制在可視範圍內。尺寸由最大內容需求決定，內容區獨立捲動，不因列表長短改變外框尺寸。
- 在窄視窗將左側導覽收成頂部可橫向捲動的功能列，保留相同內容高度、焦點順序與 Esc 返回規則；避免把桌面 5 人總覽硬縮成不可讀的小卡片。
- 共用固定頁首、主導覽、內容視口與分頁列。Tab 切換和分頁不應重置搜尋條件以外的選取狀態；關閉選單再開啟時，回到上次主功能及捲動位置。
- 每個列表頁最多呈現 20 筆，統一顯示目前範圍、總數、上一頁／下一頁及空狀態。頁面變更或篩選條件變更時將頁碼校正回有效範圍。

## 2. 各主功能內容

### 道具

- 第一層頁籤為「可使用」、「任務」、「全部」。
- 「可使用」內再分回復類與 Buff 類；只顯示目前模式、目標狀態及道具規則允許使用的項目。無法使用時保留項目並說明原因，或提供明確的「僅探索可用」提示，不讓玩家猜測。
- 道具列顯示名稱、數量、主要效果與有效目標；使用動作在本頁完成。裝備類物品導向「裝備」頁並預選對應槽位，避免行囊和裝備頁有兩套不同的比較流程。
- 「全部」可依道具類型篩選，任務道具預設不可誤用或丟棄。

### 裝備

- 預設呈現最多 5 名隊員的直向總覽，每名隊員固定一列；欄位依序為角色、武器、防具、飾品、被動功法、屬性摘要、Buff 效果。裝備欄支援 5 基礎部位及 2 飾品槽，窄內容區允許表格橫向捲動或切換至單一隊員詳細檢視。
- 武器、防具、飾品格均可直接開啟該角色、該槽位的挑選子視圖。被動欄顯示目前啟用的 weapon、parry、dodge、force 等功法及其槽位；未啟用與不可用狀態要明確區分。
- 屬性摘要至少區分「基礎值」、「裝備增減」、「目前總值」。Buff / Debuff 獨立列出來源、效果與剩餘時間或持續條件，不將暫時效果混進永久裝備加成。
- 每個隊員列提供清楚的選取狀態；點擊裝備格時，子視圖標題帶出隊員名稱和槽位，避免在多人總覽中裝錯人。

### 技能與法術

- 第一層頁籤為「可使用」、「主動」、「全部」。「可使用」依目前探索／城鎮等模式、目標和資源條件篩選；主動技依分類或消耗資源作次級篩選。
- 列表顯示施展條件、資源消耗、冷卻、目標類型及無法施展原因。探索中可使用的技能與戰鬥專用技能須以資料狀態判斷，不以前端名稱猜測。
- 被動功法仍可在「全部」檢視，顯示槽位與啟用狀態；啟用/切換後更新目前角色上下文，不離開選單。

### 角色

- 頁籤對應目前隊伍成員；每名角色顯示詳細資料、等級與經驗、HP / MP / SP（依目前資料契約）、五維、基礎屬性與裝備／效果加成明細。
- 自由點數等立即操作沿用現有服務指令。角色頁的數值口徑需與裝備頁一致，不能一處顯示基礎值、另一處把裝備值混入卻不標註。

### 隊伍

- 提供隊員編號／出戰順序調整；建議以「上移／下移」按鈕為基本操作，拖放可作為桌面輔助，不能成為唯一操作方式。
- 明確區分隊伍名冊順序（#1～#5）與戰陣盤的幾何站位。調整編號不應改變角色 identity、裝備、戰術規則或陣位；提交後由伺服器驗證並回傳最新隊伍快照。
- 若隊伍上限或隊員生死狀態限制排序／出戰，直接在操作旁說明限制。

### 陣法

- 使用「戰陣盤」與「典籍庫」兩個頁籤。戰陣盤沿用現有 5 x 3 站位編排；典籍庫沿用目前的人數篩選、條件提示和解鎖狀態。
- 典籍庫分頁改為每頁最多 20 個陣法，保留適用隊伍人數、需求職業、陣法效果、奧義及目前啟用狀態。選擇陣法前呈現人數／職業不符原因。
- 陣法切換和站位編輯留在選單內完成；陣法奧義是否可施展應顯示條件與靈威，不以只有按鈕亮暗作為唯一訊息。

### 戰術方針

- 採 Gambit 優先序規則鏈：自上而下檢查，第一條符合條件且技能可施展的規則執行。介面要把「條件 → 目標 → 動作」呈現成可掃讀的一列。
- 每條規則支援啟用／停用、上移／下移、編輯、複製及刪除；新增規則時用分步選擇條件、目標與技能，並即時顯示該角色不符合技能需求的原因。
- 提供一個簡短的規則鏈預覽及「無規則符合時」的 fallback 說明。隊長維持玩家手動控制，不要讓 Gambit 設定暗中接管隊長。

### 系統

- 將現有存檔視窗整合為「存檔」與「讀檔」頁籤，保留槽位摘要、自動存檔、空槽與覆寫流程，不另造一套檔案格式。
- 覆寫及讀檔前清楚顯示槽位、角色名稱與時間；可能覆蓋進度的動作要求確認。操作完成後留在系統頁並顯示結果。

## 3. 裝備挑選與比較子視圖

1. 點擊隊員某個裝備槽後，在選單內容區切入挑選子視圖（或同一選單上的次層覆蓋面板），不要開第二個獨立 modal。保留父頁選取的角色、槽位、篩選條件與捲動位置。
2. 候選清單只列符合該槽位且角色可穿戴的物品，可切換可裝備／全部候選並顯示不可裝備原因；候選清單同樣每頁最多 20 筆。
3. 選取候選後，在固定資訊欄並列「目前裝備」與「候選裝備」，顯示各屬性目前值、裝備後值、差值，以及新增／移除／改變的 Buff、被動觸發效果和限制條件。正向與負向差異使用文字與色彩共同標示。
4. 比較預覽由伺服器的裝備規則計算並回傳，或由共享的純領域計算器提供；不可在 UI 複製一份簡化公式，否則武器、套裝、被動與 Buff 的交互會造成預覽與實際結果不一致。
5. 玩家按「裝備」後送出既有裝備操作或明確的槽位操作；成功收到伺服器最新隊伍快照後關閉子視圖並回到原裝備頁，更新該角色列。失敗時保留比較畫面並顯示原因，不丟失選取狀態。
6. 卸下裝備也應從同一槽位流程執行，並可預覽會失去的屬性與效果；若物品已被其他操作消耗、角色狀態改變或背包已滿，重新驗證並拒絕過期操作。

## 4. 實作邊界與資料需求

- UI 只管理目前主功能、頁籤、頁碼、篩選、選中隊員與返回位置；角色屬性、物品可用性、裝備限制、比較結果、Gambit 規則有效性及存檔結果由伺服器資料決定。
- 裝備總覽需要同一隊伍快照提供每個槽位的當前物品、可用被動槽位與啟用技能、基礎／總屬性、效果來源及持續狀態。現有 DTO 缺欄位時先明確補 DTO／服務契約，再接畫面。
- 裝備預覽至少需要角色 ID、槽位、目前裝備 ID、候選物品 ID 與狀態版本；伺服器回傳差值及可否套用。正式裝備時仍重新驗證，預覽不能取代授權與規則檢查。
- 隊伍排序應以穩定角色 ID 傳遞目標順序，不以顯示名稱或目前陣列索引作 identity；既有戰陣座標保持獨立欄位。
- 延續既有模組邊界，逐步將 `party-modal.js` 拆成選單導覽與各功能 renderer；不在本次 UI 改版順手重構整個前端、存檔格式或戰鬥模型。

## 5. 建議實作順序

### Phase 1：選單殼層與既有功能遷移

- 建立固定尺寸選單框架、左側功能導覽、內容視口及共用 20 筆分頁元件。
- 將現有裝備／角色、技能書、Gambit、陣法典籍與戰陣盤接入新導覽；把背包使用與存讀檔從獨立入口導向選單對應頁。
- 保留舊快捷鍵與既有 server commands，驗證 Esc、焦點回復、窄視窗和狀態更新。

### Phase 2：道具、技能與角色資訊一致化

- 補齊分類、使用限制、頁籤、20 筆分頁、空狀態與操作回饋。
- 定義基礎值／裝備值／Buff 值的共用顯示契約，確保角色與裝備頁數字一致。

### Phase 3：裝備比較與隊伍排序

- 先完成裝備預覽資料契約和伺服器驗證，再實作槽位子視圖、並列比較、套用與返回行為。
- 實作穩定 ID 的隊伍排序指令與回傳快照；明確測試排序不會改變裝備、Gambit 或戰陣座標。

### Phase 4：操作打磨與回歸

- 加入 Gambit 規則排序／編輯流程、鍵盤操作、載入／空資料／錯誤狀態與窄視窗適配。
- 以現有資料樣本驗證 0、1、20、21 筆列表，1～5 名隊員、滿背包、屬性為負向的裝備差異、Buff 替換、不可用技能及失效候選裝備。

## 6. 驗收條件

- 選單包含八個指定主功能；主功能切換不會堆疊多個 modal，且關閉與重開可恢復合理的導覽位置。
- 道具／技能／陣法候選列表每頁不超過 20 筆；篩選、頁數、總數、空狀態及不可用原因一致。
- 裝備頁同時容納最多 5 名隊員總覽；能分辨基礎屬性、裝備增減及 Buff，並看見啟用的被動功法。
- 裝備子視圖可比較現有與候選裝備的實際屬性及效果差異；套用後返回原隊員與原槽位，並以最新伺服器狀態更新。
- 隊伍排序只調整名冊順序，不改變角色 identity、裝備、戰術方針或戰陣座標。
- 戰陣盤、典籍庫、Gambit、新增／讀取／覆寫存檔均可由選單內完成，並有成功、失敗及確認狀態。
- 桌面與窄視窗下內容不互相遮擋；鍵盤可進入、切換、返回與關閉各層視圖。
