# 陣法系統 Review 與建議 (Gemini)

## 1. 系統現狀分析
經過先前的重構與擴充，目前專案中的陣法系統已經從靜態資料演進到了動態配置，主要亮點包括：
- **動態匹配與 Fallback 機制**：基於隊伍人數 (2-5人) 自動過濾可用陣法，並在人數或條件不符時有退回基礎陣法的安全機制。
- **職業門檻 (Class Requirements)**：進階陣法 (如十字陣、鳳凰陣) 已經能透過 `requiredClasses` 驗證特定職業組合。
- **陣位與站位分離**：實裝了 `FRONT/MIDDLE/BACK` 站位，並透過 `assignedRow` 讓陣法孔位能正確覆蓋角色的預設站位。
- **UI 動態渲染**：前端 `party-modal.js` 已經能動態渲染可用陣法，並清晰顯示解鎖/鎖定原因與各孔位效果。

這套系統的底層架構（資料驅動 JSON + 領域模型 Party/FormationTemplate）非常健康，適合作為 DRPG 的核心戰術系統。

## 2. 針對 Copilot 建議的評估與補充

Copilot 的建議非常全面，特別是**狀態機 (Stability/Break)** 與 **效果規則化 (passiveEffects)** 的方向，完全切中要害。我在此基礎上，結合目前程式碼與最新的討論設計，提出進一步的實作細節與修正建議：

### 2.1 嚴格存活人數與破陣機制 (Strict Party Size matching)
Copilot 建議引入 `stability` (穩定度 0-100) 數值。這在設計上很豐富，但在傳統回合制戰鬥中可能略顯繁瑣，且增加玩家理解成本。
經過評估與討論，我們決定採用更直觀、戰術張力更強的**「存活人數破陣機制」**：
- **機制核心**：陣法的 `requiredPartySize` 不再代表「隊伍總人數」，而是「隊伍目前的存活人數」。
- **減員即破陣**：當 5 人陣法中有 1 人死亡（存活變為 4 人），因不再滿足 5 人陣法條件，系統即時廣播「隊員陣亡，陣法崩解！」，並立刻清除陣法 Buff 與清空靈威。
- **戰中變陣 (止血)**：玩家必須在戰鬥中透過戰備指揮台，手動切換至符合目前存活人數的 4 人陣法，才能重新獲得加成。
- **自動遞補排位 (Auto-mapping)**：切換為 4 人陣法時，陣法的 4 個孔位會自動依序套用到存活的 4 名隊員身上。陣亡的隊員在 UI 上會被移至角落（顯示為灰階或墓碑狀）。
- **復活重佈陣**：若在戰鬥中將隊員復活，存活人數變回 5 人，目前的 4 人陣法會再次因人數不符而失效。玩家需要再次手動切換回 5 人陣法，全員即會自動歸位。
- **優點**：讓玩家對「減員」有極大的危機感，一旦死人就會面臨失去陣法與奧義的雙重懲罰，逼迫玩家立刻做出戰術決策（復活還是換陣止血），完美契合 DRPG 的硬核風格。

### 2.2 效果規則化 (Passive Effects) 與 靈威系統
Copilot 建議將文字的 `passiveAura` 轉為可解析的 `passiveEffects`。
**Gemini 建議：**
- 遊戲中已有 `ActiveBuff` 系統，我們應該**直接複用現有的 Buff 系統**，避免發明新輪子。
- 陣法生效時（`Party.refreshFormation()`），解析 JSON 中的陣法被動，將其轉換為持續時間無限（直到切換陣法）的 `ActiveBuff`，掛載在全隊或特定站位身上。
- **陣法絕技 (Ultimate)**：應與隊伍共用資源「靈威 (Energy)」掛鉤。可以在 `Party` 實體中新增 `formationEnergy` (0-100)，每回合行動、受擊、或觸發特定職責行為時增加。滿 100 才能透過戰備指揮台施放陣法大招。破陣時靈威清零，極大地鼓勵玩家維持陣型完整。

### 2.3 站位、職責與仇恨機制的解耦
Copilot 提到 `role` (職責) 與站位的關聯。
**Gemini 建議：**
- 浪漫沙加 (Romancing SaGa) 的陣法精髓在於**「特定孔位提供極端的倍率與仇恨差異」**，而非強制要求職業。
- 目前的 `attackMultiplier` 和 `defenseMultiplier` 設計已經很好，但缺少了**仇恨控制**。
- 建議在 `FormationSlot` 增加 **`threatMultiplier` (仇恨倍率)**。例如，十字陣的前鋒位，受擊權重增加 300% (甚至自帶嘲諷效果)，而兩翼受擊權重減少 50%。
- 當戰鬥引擎選擇目標時，結合 `threatMultiplier`，就能真正實現「陣法決定誰挨打」的戰術深度，而不需要額外寫死 role 判斷。

## 3. 具體實作路徑建議 (Action Plan)

不需要一次大改，建議分成三個階段逐步深化：

### Phase 1: 戰鬥數值與仇恨對接 (高 CP 值)
1. **修改模型**：在 `FormationSlot` 新增 `threatMultiplier` 欄位。
2. **Buff 系統整合**：在 `Party.refreshFormation()` 中，根據陣法的 `attackMultiplier`、`defenseMultiplier` 生成 `ActiveBuff` 掛在隊員身上，讓前端狀態欄能看見實際數值變化。
3. **仇恨實裝**：修改敵方的 AI 目標選擇邏輯，將 `threatMultiplier` 納入權重計算。

### Phase 2: 存活人數檢測與破陣機制 (增加戰術張力)
1. **條件修改**：將 `Party.isEligibleForParty()` 的判定從總人數改為「存活人數 (Alive Count)」。
2. **事件掛鉤**：在戰鬥 FSM 的角色死亡與復活處理邏輯中，加入存活人數驗證。若人數改變導致不符目前陣法，觸發破陣。
3. **降階邏輯**：觸發破陣時，清除陣法 Buff 與靈威，輸出系統提示，並等待玩家手動變陣止血。
4. **UI 與排位遞補**：在 `party-modal.js` 實作自動遞補邏輯，讓陣法孔位依序套用給存活者，並將死亡者獨立顯示於角落。

### Phase 3: 靈威與陣法絕技 (終極回饋)
1. **資源池**：在 `Party` 與 `PartyViewDto` 中新增 `formationEnergy`。
2. **累積機制**：戰鬥回合結算時，根據存活人數與行動給予靈威。
3. **絕技按鈕**：在 UI 上實作消耗 100 靈威施放陣法專屬技能（可直接映射到對應的 `SkillTemplate`）。

## 4. 總結
目前專案的陣法系統已經越過了最困難的「資料結構建置」與「動態驗證邏輯」階段，架構非常穩固。
接下來的重點**不是重構核心，而是向外對接**——將陣法屬性與「戰鬥狀態機 (Combat FSM)」、「Buff 系統」及「仇恨計算」縫合。只要補上「仇恨倍率」與「存活人數破陣」機制，就能用最小的程式碼改動，換取最原汁原味的 DRPG 陣型戰鬥體驗。
