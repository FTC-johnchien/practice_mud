# Codex 專案檢視與動態戰鬥改善建議

> 檢視日期：2026-10-05  
> 範圍：參考 [`ARCHITECTURE.md`](../../ARCHITECTURE.md)、[`UI_PAGE_STRUCTURE.md`](../UI_PAGE_STRUCTURE.md)、[`FUTURE_IMPROVEMENTS.md`](./FUTURE_IMPROVEMENTS.md)、[`10_combat_dynamics.md`](../references/10_combat_dynamics.md) 與既有 [`Copilot_Code_Review.md`](./Copilot_Code_Review.md)，並核對戰鬥循環、DTO、前端面板、CSS、資料模型與相關文件。這是以戰鬥體驗為主的架構檢視，不是逐行安全稽核；未修改遊戲程式，也未執行測試。

## 一、摘要

專案已有可用的戰鬥底層：敵我陣位、仇恨與嘲諷、Buff、Gambit、自動戰鬥節奏、戰鬥結果及 WebSocket 狀態更新。戰鬥主舞台也有敵方陣列、目標鎖定和小隊 HUD。

目前動態感主要由自動扣血、文字日誌與定時重繪構成。玩家較難從畫面直接看出「誰正要做什麼、攻擊何時落下、剛才的操作造成什麼視覺結果」。改善不必從大型動畫框架開始：先把戰鬥變化表達成結構化事件，前端依事件做短促、可略過的動態回饋；再補上敵方預告與反制，讓動畫也承載戰術資訊。

## 二、主要發現

| 優先度 | 發現 | 程式碼與影響 | 建議 |
|---|---|---|---|
| **P1** | 戰鬥狀態缺少可供 UI 演出的事件 | `BattleViewDto` 目前帶 `inBattle`、`battleState`、敵人快照、選取目標及 `List<String> logs`；`BattleEnemyViewDto` 沒有意圖、行動階段或預定目標欄位。戰鬥訊息在 `DrpgCombatLoop` 多以自由文字寫入 `battleLogs`。前端收到快照後能更新血條，卻無法穩定判斷這次變化是命中、閃避、格擋、治療、死亡或蓄力。 | 定義精簡的 `CombatEvent`（事件 ID、序號／時間、種類、來源、目標、數值、技能 ID），在既有結算點產生事件；DTO 傳遞近期事件，前端以事件驅動演出、文字日誌仍保留敘事。先涵蓋普通命中、暴擊、閃避／格擋、治療、擊倒與技能施放。避免從日誌文案反向解析動畫。 |
| **P1** | 5 分鐘固定逾時仍會中止持續進行的戰鬥 | `BattleContext` 的 `maxDurationMs` 預設 300,000ms，`isTimedOut()` 同時檢查絕對時長與 10 分鐘閒置；`DrpgCombatLoop` 每輪無條件檢查。因此玩家持續操作也會在 5 分鐘後被中斷，與 `FUTURE_IMPROVEMENTS.md` Combat-02 對一般戰鬥的規劃互相矛盾。 | 在加入長時間首領戰與動態戰鬥前，先決議並分離閒置熔斷與絕對安全上限。若一般戰鬥不應被固定時間截斷，預設停用絕對時限或依模式明確配置；以有效操作觸碰活動時間。 |
| **P1** | 敵方招式目前偏向招式名稱與傷害敘述，預告／反制資料尚未接入 | `DrpgEnemyTacticsService.selectEnemyMove()` 可從種族或技能資料選招式文字；敵方攻擊時機由 `nextAttackTime` 控制，但當前 `BattleEnemyViewDto` 不回傳行動意圖。玩家多在日誌描述攻擊後才知道發生什麼。 | 落實路線圖 ENEMY-ACTION-01：先做少數通用行動，包含目標規則、蓄力時間、效果及是否可打斷；加入 `IDLE → TELEGRAPH → RESOLVE → RECOVERY` 行動狀態，讓 UI 顯示蓄力條、目標提示與結算時機。 |
| **P2** | 戰鬥卡片有視覺回饋基礎，但 DOM 事件及樣式耦合提高擴充成本 | `battle-panel.js` 已依敵人／隊伍結構做局部更新，但卡片使用 `card.onclick`，並在多處直接設定 `style` 與組合 HTML。若逐個新增動畫狀態、浮字與危險標記，渲染函式會更難維護。動態文字已有部分 `escapeHtml()`；問題主要是呈現與事件責任糾纏，不代表所有 `innerHTML` 都有漏洞。 | 增加演出時一併建立面板容器事件委派和 CSS 狀態 class（如 `is-attacking`、`is-hit`、`is-telegraphing`、`is-defeated`）；保持現有資料轉義。將卡片內容渲染與動畫觸發分開，避免每次快照更新都重建／重播整張卡片。 |
| **P2** | 戰鬥畫面的「動態」規格和目前實作有差距 | `UI_PAGE_STRUCTURE.md` 規劃敵方 5×5 陣列及更細分的戰鬥子模組（`battle-enemies-view.js`、`battle-command-dock.js`、`battle-party-deck.js`），目前 `rg --files` 未找到這些子模組；現有主要戰鬥渲染仍集中於 `battle-panel.js`。參考文件 `10_combat_dynamics.md` 的飄字建議也尚未形成事件／UI 契約。 | 先修正文檔標示，區分「現況」與「目標規格」；待單一垂直切片累積複雜度後，再按敵人視圖、隊伍甲板、演出層拆分。不要只為符合文件中預想的檔名而拆檔。 |
| **P2** | 首領階段及 SAN 異變等效果仍有 Java 專屬分支 | `DrpgCombatLoop` 處理 SAN 走火入魔流程及依 `aberration-` ID 特判戰鬥敘述；敵方招式抽取和行動效果也沒有完整的資料驅動 action 契約。新增敵人機制時容易繼續累積名稱分支。 | 先讓共通行動效果、目標選擇及階段觸發以資料描述；保留 Java 作為通用效果執行器。依 `FUTURE_IMPROVEMENTS.md` 既有 ENEMY-ACTION-01、COMBAT-REACT-01、COMBAT-DATA-DOC-01 推進，避免重複建立平行待辦。 |
| **P3** | 架構文件中有多處歷史資訊可能被誤認為現況 | 文件有已拆分 CSS、`party-modal.js`、Legacy 除役等紀錄，也包含不同時間點的測試數字；UI 頁面規格仍混合目前描述與預期模組。這會讓後續審查無法只靠文件判斷程式實況。 | 每份文件明確標記現況／目標／歷史里程碑；測試數字保留在有日期的落地紀錄，不在摘要中視為即時狀態。每次戰鬥 DTO 或模組結構變更後同步更新 UI 規格。 |

## 三、如何讓戰鬥畫面更生動且仍然清楚

### 第一層：低風險演出回饋

以既有事件資料驅動短動畫，不必等待完整敵方技能系統：

- 命中時在目標卡片上浮出傷害數字；暴擊放大並使用強調色，治療用綠色，閃避／格擋顯示結果標記。
- 受擊卡片做短暫亮光或輕微震動；死亡卡片淡出／倒下後移除，勝利時顯示簡短結算過場。
- 攻擊者與目標之間短暫顯示方向連線或光束；群體技能以受影響隊列或卡片同步提示。
- 血條以 CSS transition 平滑過渡至新值；事件 ID 去重，避免同一 WebSocket 快照重送時重複播動畫。
- 支援 `prefers-reduced-motion`，並讓演出時間短、動畫不阻擋點擊與技能操作。

這一層只改呈現方式，不改傷害與戰鬥平衡；事件不完整時仍可以快照更新血條，維持狀態正確。

### 第二層：敵方預告與玩家選擇

在第一層事件管線穩定後，敵人可進入明確的蓄力狀態。敵人卡片顯示招式名稱、目標或範圍、倒數條及可否打斷；危險攻擊也在我方陣列標出受威脅隊員。這讓攻擊動畫同時傳達時序和目標，而不是單純裝飾。

第一個可玩切片建議包含：普通敵人單體重擊、一個首領前排掃擊、玩家一種打斷或防守反制。成功打斷要讓敵人進入短暫失衡；未反制則照常結算並呈現受擊反饋。先驗證此循環是否有趣，再加首領階段、地格危險區或召喚物。

### 第三層：隊友自動戰術看得懂

將「敵人正在蓄力」提供給 Gambit 條件；隊友可依規則打斷、施盾或治療。日誌與戰鬥畫面應簡短說明觸發條件、耗用資源與結果，玩家仍能辨認為何隊友做出該行動。自動 AI 不應自動消除所有攻擊機制。

## 四、建議實施順序

1. **決議逾時規格（P1）**：一般戰鬥、訓練、首領戰分別定義閒置與絕對安全上限。
2. **戰鬥事件與前端回饋（P1）**：建立事件 DTO 與去重方式；先呈現傷害、治療、格擋、閃避、死亡等短演出。
3. **敵方意圖垂直切片（P1）**：新增一個蓄力攻擊，串起行動狀態、WebSocket DTO、敵方卡片和玩家打斷／防守。
4. **首領與 Gambit 互動（P2）**：把同一 action 契約用在一個首領掃擊與一條隊友反制 Gambit，之後才擴成階段機制。
5. **資料化特例及文件整理（P2/P3）**：遷移 SAN 異變特例、同步架構與頁面現況、保留有日期的測試紀錄。

## 五、驗收條件

- 每個視覺效果都由有型別的戰鬥事件觸發；收到重複事件不會重播，缺漏事件時快照仍可校正畫面。
- 玩家可在敵方攻擊結算前看見招式、目標、倒數和反制方式；預告至少跨越一個可互動的更新窗口。
- 命中、暴擊、治療、閃避、格擋與死亡有清楚且辨識度不同的回饋，且不取代文字戰報。
- 玩家可操作時動畫不鎖住控制；減少動態效果設定會降低／移除非必要動態。
- 自動化測試使用可控時鐘及固定隨機來源覆蓋預告、打斷、結算、重複事件與逾時邊界；再以一場普通戰和一場首領戰做畫面驗收。

## 六、結論

建議將下一步拆成「戰鬥事件驅動的視覺回饋」與「敵方預告／反制」兩個相接的工作。前者能較快讓現有戰鬥有動態節奏，後者再把動態轉化成戰術決策。這和既有 `FUTURE_IMPROVEMENTS.md` §13 的方向一致；本報告補充了目前 UI／DTO 的實作落差、最小演出管線及其驗收方式。
