# 戰鬥區塊演出效果：建議與執行計畫

> 日期：2026-10-05  
> 範圍：在現有戰鬥區塊加入攻擊、命中／格擋／閃避反應，以及依傷害類型區分的浮動數字；保留訊息區戰鬥紀錄。  
> 參考：[Claude 方案](./Claude_battle_presentation_effects.md)、[Copilot 方案](./Copilot_battle_presentation_effects.md)

## 建議摘要

建議先做一個「看得懂戰鬥結果」的版本，再增加招式風格：

1. 後端在傷害實際結算時建立結構化戰鬥事件，記錄攻擊者、實際目標、傷害量、傷害屬性及命中結果。既有文字 log 照常保留。
2. 前端在戰鬥舞台上新增不攔截點擊的特效層，播放短促受擊反應與浮動傷害／治療數字。攻擊效果、元素色彩以可重用的少數預設逐步加入。
3. 第一階段先支援目前已有的普攻及敵方防禦判定，不新增暴擊機率、命中規則或範圍目標規則。
4. 單體、全體與未來的一排攻擊，都以後端實際結算的 `hits` 作為唯一命中清單；前端不可自行猜哪些單位會受傷。

第一個可交付版本應讓玩家一眼看出「誰打誰、結果如何、扣了多少」。先不做複雜粒子、鏡頭震動、音效或死亡殘影。

## 現況與範圍界線

目前 [DrpgCombatLoop.java](../../src/main/java/com/example/htmlmud/domain/dungeon/battle/DrpgCombatLoop.java) 在隊員普攻、敵方攻擊和技能結算處已掌握傷害與目標；敵方攻擊另有 [DefenseResolver.java](../../src/main/java/com/example/htmlmud/domain/dungeon/battle/DefenseResolver.java) 提供命中、暴擊、格擋、招架、閃避、未命中等結果。不過結果主要以文字 log 輸出。[BattleViewDto.java](../../src/main/java/com/example/htmlmud/domain/dungeon/dto/BattleViewDto.java) 是狀態快照，並不代表剛發生的攻擊事件。

前端 [battle-panel.js](../../src/main/resources/static/js/panels/battle-panel.js) 負責戰場卡片呈現，遇到敵人死亡或陣列變化可能重建卡片；[mud-core.js](../../src/main/resources/static/js/mud-core.js) 負責 WebSocket 訊息分派。因此，事件應與狀態快照分開傳送，效果播放時再查找當下的目標 DOM。

| 項目 | 現有狀況 | 對規劃的影響 |
|---|---|---|
| 敵方攻擊防禦結果 | 已有 `DefenseOutcome` 和最終傷害 | 可直接驅動受擊、格擋、閃避等反應 |
| 隊員普攻 | 有目標、武器與實際傷害；不一定有暴擊／未命中判定 | 先呈現既有結算，不自行虛構暴擊 |
| 技能範圍 | 有單體與 AOE 結算路徑 | 事件列出每個實際受影響目標 |
| 一排攻擊 | 需先確認是否已有明確的結算規則 | 規則未定義前只規劃資料欄位，不加入新攻擊機制 |
| 屬性資料 | 各技能／敵人資料完整度需逐一核對 | 缺值用 `UNKNOWN`，不從 log 文句猜顏色或屬性 |
| 敵我單位定位 | 現有卡片有索引屬性 | 增加穩定單位 ID，避免重排後播到錯誤目標 |

## 呈現原則

### 事件、狀態與文字各司其職

- `DRPG_STATE` 描述「現在」的 HP、存活狀態和陣形。
- 新增的 `BATTLE_EVENTS` 描述「剛才發生了什麼」，只攜帶後端已結算事實。
- 文字 log 繼續保留完整敘事與非動畫資訊。特效不取代 log，前端也不解析 log 來還原戰鬥規則。

### 顏色表示屬性，標記表示結果

傷害屬性和暴擊等判定是兩個維度，應採正交呈現：屬性決定數字顏色，暴擊用放大、描邊或「暴擊」標籤表示。這樣火焰暴擊仍看得出是火焰傷害。

| 類別 | 建議呈現 | 注意事項 |
|---|---|---|
| 物理傷害 | 近白或暖白數字、深色描邊 | 與場景背景保持對比 |
| 一般／未知法術 | 藍紫或中性色 | 未知屬性不要推測元素 |
| 火、冰、雷、毒等明確元素 | 橘、冰藍、黃、綠等固定色 | 只在事件有可靠屬性資料時使用 |
| 暴擊 | 保留原屬性色，放大並標示「暴擊」 | 不用另一種顏色覆蓋屬性資訊 |
| 格擋、招架、閃避、未命中 | 短文字標籤加不同動態反應 | 完全未受傷時不顯示 `0` 傷害 |
| 治療 | 綠色 `+N` | 與傷害使用不同符號和樣式 |

傷害數字以目標 HP 變化為準：傷害顯示 `−N`，治療顯示 `+N`。若格擋仍造成殘餘傷害，顯示「格擋 −N」；完全格擋、閃避或未命中只顯示結果標籤。

### 動作要短而清楚

一般受擊反應約 250–450ms，單次事件約 500–900ms。單體攻擊可用出手者短促前移／亮起、目標輕震／閃白及浮動數字；格擋用盾牌或金屬碰撞提示，閃避用側移或殘影，未命中讓攻擊軌跡掠過即可。AOE 共用一次起手效果，再依目標清單錯開結果數字，避免整片畫面同時閃爍。

動畫優先使用 `transform` 與 `opacity`。FX layer 設定 `pointer-events: none` 和 `aria-hidden="true"`。支援 `prefers-reduced-motion`：縮短或取消位移、震動和閃爍，但保留靜態數字與文字標籤。

## 事件資料建議

MVP 的事件模型保持精簡。以下為概念範例，實際 Java 欄位應以現有 ID、DTO 與序列化慣例調整：

```json
{
  "type": "BATTLE_EVENTS",
  "battleId": "battle-123",
  "events": [{
    "seq": 42,
    "kind": "ATTACK",
    "actor": { "side": "PARTY", "id": "member-1" },
    "action": { "weaponType": "SWORD", "skillId": null, "skillName": null },
    "shape": "SINGLE",
    "damageType": "PHYSICAL",
    "hits": [{
      "target": { "side": "ENEMY", "id": "enemy-3" },
      "outcome": "HIT",
      "amount": 42,
      "absorbed": 0,
      "killed": false
    }]
  }]
}
```

- `battleId` 與每場戰鬥遞增的 `seq` 用於切場清理、排序與去重。
- `actor`、`target` 使用穩定 ID 和陣營；索引只作為備援資訊，不作唯一定位依據。
- `kind` 至少涵蓋 `ATTACK`、`SKILL`、`HEAL`。後續有準確結算資料時再加 `SHIELD`、`DOT_TICK`、`HOT_TICK` 等。
- `shape` 表示呈現範圍，例如 `SINGLE`、`ALL`、未來的 `ROW`；實際命中永遠以 `hits` 為準。
- `damageType` 缺乏可靠資料時設 `UNKNOWN`。`weaponType` 和 `damageType` 可分別決定攻擊動畫與傷害配色。
- `outcome` 沿用現有判定；`amount` 是實際施加的傷害／治療量。若護盾吸收量無法準確取得，省略或給明確的未知值，不估算。

事件應在傷害、治療或防禦結果確定的結算位置建立，不在前端重算。自動戰鬥可與 tick 狀態廣播一起送出批次事件；手動施放技能由其實際結算路徑立即送出，避免等到下一次 tick。也需涵蓋最後一擊、戰鬥結束、逃跑與錯誤清理，避免漏送或跨場重播。

## 前端結構建議

在戰鬥舞台中放置覆蓋式 FX layer，動畫元素不直接附掛在會被重建的敵人卡片上。播放前以 `getBoundingClientRect()` 將目標卡片位置換算到 FX layer 座標；每次播放重新查 DOM，不保留可能失效的節點。

| 元件 | 職責 |
|---|---|
| WebSocket 分派 | 收到 `BATTLE_EVENTS` 後轉交事件控制器 |
| `BattleFxDirector` | 依場次與序號去重、限流、排序及清理 |
| 預設對照表 | 由動作種類、武器組、傷害屬性和結果選動畫，不承載戰鬥運算 |
| 浮動結果文字 | 顯示傷害、治療、暴擊、格擋、閃避等數字／標籤 |
| FX layer 與 CSS | 顯示短動畫；對卡片重建保持獨立 |

武器效果第一版只需分斬擊、鈍擊、投射物、施法／法器、徒手等少數組別。法術共用動畫骨架，再依元素調整色彩與光暈；不要為每個技能各做一套動畫。

## 分階段執行

### Phase 0：確認資料與結算位置

1. 列出普攻、敵方攻擊、技能單體／AOE、治療、護盾、DoT／HoT、反擊等來源。
2. 為每個來源核對 actor、穩定 target ID、實際傷害／治療、outcome、武器與屬性欄位；缺資料標記未知，不用 log 反解析。
3. 確認自動 tick、手動技能與戰鬥結束流程的事件送出時機。
4. 確認敵我卡片均可由穩定 ID 定位，且切換戰鬥時能清除舊場事件。

**完成條件：**每種 MVP 事件都有明確的結算埋點、資料來源和 DOM 定位方式。

### Phase 1：普攻與防禦結果 MVP

1. 建立小型事件 DTO、必要 enum 及每場戰鬥的事件序號；保留既有 log。
2. 在隊員普攻和敵方攻擊的實際結算處建立事件。沿用敵方攻擊 `DefenseResolver` 結果；不新增我方暴擊／未命中機率。
3. 新增 WebSocket `BATTLE_EVENTS` 路由，與 `DRPG_STATE` 分離。
4. 為我方與敵方卡片加入穩定 `data-unit-id`、`data-unit-side`，在戰場建立 FX layer。
5. 實作基礎命中數字、受擊反應，以及暴擊、格擋、招架、閃避、未命中的結果標籤；零傷害結果不顯示 `−0`。
6. 加上場次切換清理、序號去重、過期目標略過、事件佇列與同時特效上限，以及減少動態支援。
7. 比對畫面數字和 log／實際 HP 變化，確認快照重繪不會把效果播到其他單位。

**MVP 驗收：**敵我攻擊均在正確卡片顯示；結果標籤清楚；傷害數字等於實際結算；死亡重繪、切場與快速連續事件不造成錯位或舊效果殘留；訊息區紀錄不變。

### Phase 2：技能、治療與範圍攻擊

1. 在技能實際套用傷害、治療、護盾的位置產生事件。
2. AOE 使用單一事件和多個 `hits`；共用一次起手動畫，再逐目標顯示實際結果。
3. 只映射資料中可靠存在的傷害屬性，其他先用 `UNKNOWN`。
4. 依結算資料完整度加入治療、護盾和 DoT／HoT。避免沒有準確數字時呈現誤導性的跳字。
5. 先不做死亡殘影；優先確保致死一擊的傷害數字在卡片移除前仍可見（必要時複製短暫的純視覺殘影）。

**驗收：**單體與 AOE 的目標、HP 變化、log 和動畫一致；同一 AOE 不重複播放全場起手效果。

### Phase 3：武器與法術屬性風格

1. 建立小型動畫預設表，支援斬擊、鈍擊、投射物、施法和徒手。
2. 以 `weaponType`、`damageType`、`kind` 選預設，不使用技能名稱或 log 文句推測。
3. 先用 CSS transform／opacity 實作簡潔效果；只有證明有需要時才引入 SVG 或更複雜渲染。
4. 檢查前後排、大小型敵人、長名稱、視窗縮放及多目標同時命中。

**驗收：**常見武器組與已知法術屬性能區分，畫面仍易讀，不因每次普攻過度閃爍或震動。

### Phase 4：獨立遊戲規則與選配效果

- 若要新增「打一整排」，先定義前後排推進、目標排序、無有效目標等規則，再由後端選出實際目標並回傳 `hits`。
- 若要新增我方暴擊／未命中，先定義機率、命中模型、裝備屬性影響和平衡測試；演出只使用真正的判定結果。
- 完成基本效果後，再評估死亡動畫、音效、鏡頭震動及完整／精簡／關閉設定。

這些會影響玩法或擴大維護範圍，不應作為呈現 MVP 的前置條件。

## 驗收與主要風險

### 後端核對

- 事件的 actor、target、傷害量、outcome 與實際 HP 變更吻合。
- 格擋殘傷與完全閃避／未命中不混淆；不重複計入反擊、DoT 或死亡傷害。
- `battleId`／`seq` 單調且正確；手動技能、勝敗結算、取消流程不漏事件。
- 選填動畫欄位缺漏不得影響戰鬥或 WebSocket 快照。

### 前端核對

- 覆蓋命中、暴擊、格擋殘傷、完全格擋、招架／反擊、閃避、未命中、AOE 與治療。
- 多事件連續抵達、目標死亡／重繪、resize、分頁隱藏後回來時不錯位、不累積過期佇列。
- FX layer 不攔截操作；減少動態模式仍保留結果文字和數字。
- 文字、圖示、大小與動畫共同表示結果，不只依賴顏色。

| 風險 | 建議處理 |
|---|---|
| 只在自動戰鬥 loop 發事件 | 手動技能在共用結算路徑建立並送出事件 |
| 使用陣列 index 定位 | 使用場次、陣營與穩定單位 ID |
| 前端自行決定範圍目標 | 後端列出已結算的 `hits` |
| 事件到達時卡片已重建 | 播放前重新查 DOM；找不到則略過視覺效果，不影響狀態 |
| 高頻／大量特效遮擋畫面 | 限制佇列與同時元素數，AOE 合併起手動畫並錯開數字 |
| 缺屬性資料造成錯誤顏色 | 顯示中性色並標記 `UNKNOWN`，待資料來源補齊 |

## 建議落地順序

先完成 Phase 0 和 Phase 1，確認事件與目標定位，再試玩調整數字大小、停留時間、顏色對比與演出頻率。之後加入 Phase 2 技能和 AOE，再依實際回饋製作 Phase 3 武器／屬性風格。排攻擊、我方新暴擊規則及音效等另行定義。

如此可先解決戰鬥「只有訊息、看不到發生什麼事」的問題，同時確保畫面表現忠實反映實際戰鬥結算。
