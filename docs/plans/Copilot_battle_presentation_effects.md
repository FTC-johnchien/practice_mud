# 戰鬥區塊演出效果：建議與執行計畫

> 日期：2026-10-05  
> 範圍：在現有戰鬥區塊加入攻擊、命中反應與浮動數字；保留訊息區戰鬥紀錄。  
> 相關既有規劃：[Claude_battle_presentation_effects.md](./Claude_battle_presentation_effects.md)

## 1. 建議摘要

建議把「戰鬥看起來有反應」拆成兩層，先讓玩家看懂結果，再逐步增加華麗程度：

1. **先補上結構化戰鬥事件**：後端目前會計算傷害與防禦結果，但大部分只把結果寫成戰鬥文字；前端收到的是狀態快照，因此不知道攻擊者、目標、傷害屬性與命中結果。保留原有訊息紀錄，額外傳送短小的事件資料。
2. **第一版先做「受擊反應 + 浮動數字」**：被打的卡片短暫閃光或抖動，格擋/閃避使用不同反應，傷害或治療數字從實際目標位置跳出。這比一開始做大量粒子或全螢幕特效更容易辨識，也最直接改善目前「只在訊息區有戰鬥感」的問題。
3. **第二版再加攻擊來源演出**：依武器組別、法術屬性與技能類型選擇少量、可重用的動畫預設，而不是每個技能都寫一套動畫。
4. **把會改變戰鬥規則的需求分開**：例如新增我方暴擊、未命中或「打一整排」目標選擇，都不只是表現層功能，會改變傷害或命中對象。應另行定義規則與測試，不要為了做動畫順便改戰鬥平衡。

**建議的第一個可交付版本（MVP）**：普攻與目前已存在的敵方攻擊都能顯示目標反應；傷害、暴擊、格擋、招架、閃避與未命中能辨識；訊息紀錄維持原狀。先不做排攻擊、複雜粒子、鏡頭頓格與音效。

## 2. 現況與限制

以下是依目前程式碼整理出的起點：

- 戰鬥畫面已經有敵方陣列與我方戰陣卡片，敵人會因死亡與陣列變化而重繪：[battle-panel.js](../../src/main/resources/static/js/panels/battle-panel.js)。
- 我方卡片目前以 `data-member-idx` 定位，敵方卡片以 `data-enemy-index` 定位；加上穩定的單位 ID，會比單靠陣列索引更能抵抗重排或快照更新。
- `DefenseResolver` 已經產生 `HIT`、`CRIT`、`BLOCKED`、`PARRIED`、`DODGED`、`MISS` 等結果，且帶有最終傷害值：[DefenseResolver.java](../../src/main/java/com/example/htmlmud/domain/dungeon/battle/DefenseResolver.java)。
- `DrpgCombatLoop` 會處理我方普攻、敵方攻擊、技能效果並定期廣播戰鬥狀態；普攻和技能傷害目前主要透過文字 log 呈現：[DrpgCombatLoop.java](../../src/main/java/com/example/htmlmud/domain/dungeon/battle/DrpgCombatLoop.java)。
- 前端 WebSocket dispatcher 目前處理 `DRPG_STATE` 等訊息型別，應新增獨立事件路由，而不是把短暫動畫硬塞進狀態快照：[mud-core.js](../../src/main/resources/static/js/mud-core.js)。
- 現有戰鬥 DTO 是快照，包含敵人、目標索引與 logs，沒有「某單位剛攻擊某單位」的事件：[BattleViewDto.java](../../src/main/java/com/example/htmlmud/domain/dungeon/dto/BattleViewDto.java)。
- 技能有單體與 AOE 路徑，但前端敵方格盤還有重力下落／有效排位邏輯。因而「一整排」的目標範圍，必須先由後端定義並回傳實際命中對象，不能只讓前端猜畫面上的一排。

### 2.1 需要明確區分的概念

| 概念 | 範例 | 是否只影響演出 |
|---|---|---|
| 攻擊者、目標、最終傷害 | 隊員 A 攻擊敵人 B，造成 42 | 否，這是已結算的戰鬥事實 |
| 防禦判定 | 格擋、招架、閃避、暴擊 | 通常不是；應使用戰鬥系統已算出的判定 |
| 傷害屬性 | 物理、火、冰、雷、毒 | 不一定；屬性可能也影響抗性，視現有戰鬥規則而定 |
| 範圍 | 單體、全體、一排 | 否；一排必須定義目標選擇及傷害結算 |
| 武器動畫、色彩、粒子 | 劍光、箭矢、火花 | 是，可以安全地由前端決定 |

## 3. 設計原則與建議預設

### 3.1 事件與狀態分離

- `DRPG_STATE` 繼續負責「現在的 HP、站位、存活狀態」。
- 新增 `BATTLE_EVENTS` 負責「剛才發生了什麼」。
- 原有文字訊息保持不變，仍是完整敘事與文字替代資訊；視覺效果不應取代 log。
- 事件只攜帶呈現所需的已結算事實，不讓前端重新擲骰、推導目標或計算傷害。

### 3.2 以目標為中心呈現傷害

建議統一使用「目標的 HP 變化」表示數字：傷害為 `−42`，治療為 `+42`。同一套方向規則適用於敵人與隊員，玩家不需猜正數代表打出多少、負數代表受到多少。格擋但仍受傷時顯示 `格擋 −N`；完全閃避或未命中顯示「閃避／未命中」，不要顯示令人困惑的 `0`。

### 3.3 顏色與判定採用正交編碼

傷害顏色表示**傷害屬性**；字級、描邊、圖示或短標籤表示**暴擊／格擋／來源**。不要讓暴擊把火傷顏色改成另一個完全無關的顏色，否則玩家無法同時讀出兩種資訊。

顏色建議先控制在少數清楚類別：

| 類別 | 建議視覺 | 說明 |
|---|---|---|
| 物理 | 近白色，深色描邊 | 與背景保持足夠對比 |
| 一般法術 | 藍色 | 當事件沒有更具體的元素屬性時使用 |
| 火／冰／雷／毒 | 橘／冰藍／黃／綠 | 只有後端事件明確提供屬性時才套用 |
| 暴擊 | 保留原屬性色，放大並加「暴擊」標記 | 不和屬性顏色混為一談 |
| 治療 | 綠色並加 `+` | 不使用傷害色表 |
| 格擋／招架／閃避／未命中 | 鋼灰／金色／青色／灰色標籤 | 狀態文字與動態效果要可讀 |

以上顏色應在實際戰鬥背景下檢查對比度；不能只靠顏色傳達結果，還要保留文字或圖示。

### 3.4 控制演出節奏

- 單次事件建議約 **500–900ms** 完成；一般受擊反應約 **250–450ms**。
- AOE 事件可依命中清單錯開短延遲，但總演出不要長到落後狀態快照很多。
- 高頻攻擊同目標的數字應錯開或合併，並限制同時存在的 DOM 特效數量。
- 事件抵達時重新查找目標卡片，不長期保存 DOM 節點；卡片可能因死亡、排位變化或重繪而被取代。

### 3.5 動態與無障礙

- 動畫優先使用 `transform` 和 `opacity`，避免每幀改變會觸發版面重排的屬性。
- 尊重 `prefers-reduced-motion`：縮短或取消位移、震動、閃爍，但仍保留靜態數字與結果標記。
- 特效層使用 `pointer-events: none`，不可遮擋點選目標或戰鬥操作。
- 特效層標記 `aria-hidden="true"`；文字 log 保留作為完整的非動畫資訊來源。

## 4. 建議事件格式

第一版只需涵蓋攻擊、技能、治療與防禦結果，不必一次定義所有將來的事件種類。

```json
{
  "type": "BATTLE_EVENTS",
  "battleId": "battle-123",
  "events": [
    {
      "seq": 42,
      "kind": "ATTACK",
      "actor": { "side": "PARTY", "id": "member-1" },
      "action": { "weaponType": "SWORD", "skillId": null, "skillName": null },
      "shape": "SINGLE",
      "damageType": "PHYSICAL",
      "hits": [
        {
          "target": { "side": "ENEMY", "id": "enemy-3" },
          "outcome": "HIT",
          "amount": 42,
          "absorbed": 0,
          "killed": false
        }
      ]
    }
  ]
}
```

欄位建議：

- `battleId`：切換戰鬥時識別批次，避免前一場事件在下一場播放。
- `seq`：同一場戰鬥中單調遞增，用於排序與去重。若加入重連重播，應一併定義事件保留時間及重播策略。
- `actor`、`target`：以穩定單位 ID 定位，`side` 區分敵我；索引可作為診斷或舊資料相容欄位，不應是唯一識別。
- `kind`：例如 `ATTACK`、`SKILL`、`HEAL`、`SHIELD`、`DOT_TICK`、`HOT_TICK`。MVP 可先支援 `ATTACK`、`SKILL`、`HEAL`。
- `shape`：呈現用的攻擊形狀；MVP 至少 `SINGLE` 和 `ALL`。實際被打到的單位永遠以 `hits` 為準。
- `damageType`：明確表示已知的屬性；未知時使用 `UNKNOWN`，前端採一般物理/中性色，不以技能名稱或文字猜測。
- `outcome`：使用既有防禦結果；我方攻擊目前若沒有暴擊判定，不可偽造 `CRIT`。
- `amount`：實際套用到目標 HP 的數值（非未套用減免前的 raw damage）；治療事件使用正值。
- `absorbed`：若現有規則能提供護盾吸收量才傳送；沒有可靠數值時不應估算。
- `killed`：用於後續死亡演出；MVP 可以先依目標 HP 快照呈現，不必先做死亡殘影。

**傳送時機建議**：自動戰鬥可在每個 tick 的狀態廣播附近批次送出非空事件；手動技能如果由其他命令路徑直接結算，應在該結算路徑或共用的戰鬥事件發佈器立即送出，避免玩家看見文字和狀態已變、動畫卻等到下一個 tick。需確認最後一擊、勝敗結算、例外與取消流程不會遺失已排隊事件。

## 5. 前端演出規劃

### 5.1 特效層

在既有戰鬥舞台內加入一個覆蓋式 FX layer，讓浮動數字與飛行特效不因敵人卡片重建而消失。以 `getBoundingClientRect()` 換算卡片相對於 FX layer 的座標。敵我卡片新增穩定的 `data-unit-id` 與 `data-unit-side`，並維持目前點選與渲染邏輯。

建議的職責切分：

| 模組 | 職責 |
|---|---|
| WebSocket 路由 | 識別 `BATTLE_EVENTS`，轉交給演出控制器 |
| `BattleFxDirector` | 依 `battleId`、`seq` 去重，限制佇列與同時演出數量，處理清場 |
| `fx-presets` | 由事件類型、武器組、傷害屬性選出一組演出，不放戰鬥計算 |
| `floating-text` | 建立傷害、治療及閃避/格擋等結果標記 |
| FX CSS | 定義短動畫、減少動態模式與屬性配色 |

可先把 CSS 和少數前端 helper 放在既有靜態資源結構中；只有當演出種類增加到難以維護時，才拆成多個模組，避免第一階段為了架構而架構。

### 5.2 演出對照

| 輸入事件 | 出手者／攻擊表現 | 目標／結果表現 |
|---|---|---|
| 武器普攻 | 出手卡片短促朝目標方向前移或亮起；依武器組套用斬擊、鈍擊、投射物或徒手衝擊 | 目標閃白/輕震，浮出物理傷害數字 |
| 法術攻擊 | 施法卡片短暫亮起；飛行光點或單一屬性衝擊，不同元素共享動畫骨架 | 保留元素色，命中時短暫屬性光暈並跳出傷害 |
| 一般命中 | 可略過獨立攻擊飛行物，優先保證反應清晰 | 目標短暫閃白、輕微抖動，顯示 `−N` |
| 暴擊 | 僅在後端真的判定暴擊時使用；攻擊效果稍放大，不需額外全屏閃光 | 數字放大並加「暴擊」字樣，目標較強但短暫的受擊反應 |
| 格擋 | 短暫盾牌/金屬碰撞提示 | 卡片輕震或不移動，顯示「格擋」及實際剩餘傷害 |
| 招架 | 短促交叉火花 | 顯示「招架」；若反擊另有傷害事件，反擊傷害在反擊事件目標上呈現 |
| 閃避 | 攻擊軌跡掠過或快速淡出 | 目標側移/殘影後復位，顯示「閃避」 |
| 未命中 | 出手效果掠過目標即可 | 只顯示小型「未命中」，不要錯誤觸發受擊抖動 |
| 治療 | 綠色光點上升或柔和亮起 | 目標顯示 `+N`；AOE 治療逐個目標錯開但不播放多次全場光效 |
| AOE | 一次區域脈衝作為起手 | 依 `hits` 給各目標結果與數字；限制波次時間，避免所有卡片同時閃爍 |

**武器分類不要一開始細分到每個武器 enum**。第一版先分成：斬擊類、鈍擊類、投射類、法器/施法類、徒手/其他。之後依玩家測試與實際武器種類，再調整分類。

## 6. 分階段執行步驟

### Phase 0：確認資料與演出定位

1. 列出每種實際戰鬥來源：隊員普攻、敵方攻擊、技能單體、技能 AOE、治療、護盾、DoT/HoT、反擊。
2. 對照每個來源已存在的攻擊者、目標、最終傷害、判定結果與傷害屬性；缺資料先標記為「未知」，不要用 log 字串反解析作為正式資料來源。
3. 確認事件送出路徑涵蓋自動 tick 和玩家手動技能，並確認戰鬥結束、逃跑、取消、錯誤時佇列會清理或最後送出。
4. 確認敵我兩側可用穩定 ID 對到渲染卡片。

**完成條件**：有一份明確欄位清單，且能指出每一種 MVP 事件在哪個結算位置產生。

### Phase 1：事件管線與可見 MVP

1. 定義小型事件 DTO 與允許的 enum 值；新增事件佇列或共用發佈機制，讓事件與原有 log 並行。
2. 先埋點隊員普攻及敵方攻擊。敵方攻擊直接沿用 `DefenseResolver` 的結果與最終傷害；隊員普攻先回報現有命中行為，不加新隨機規則。
3. 在 WebSocket 路由新增 `BATTLE_EVENTS` 處理；收到快照與事件時，均不重算戰鬥狀態。
4. 在敵我卡片建立穩定 DOM 定位屬性；在戰場內加入 `pointer-events: none` 的 FX layer。
5. 實作基本受擊 class 與浮動結果文字；支援 `HIT`、`CRIT`、`BLOCKED`、`PARRIED`、`DODGED`、`MISS`。
6. 實作 `battleId` 切換清場、`seq` 排序/去重、過期目標忽略、同時元素上限及 `prefers-reduced-motion`。
7. 保留戰鬥文字 log，逐項比對視覺數值與訊息中的傷害結果一致。

**MVP 驗收**：

- 隊員攻擊敵人時，數字出現在正確敵方卡片；敵人攻擊隊員時，數字出現在正確我方卡片。
- HIT、暴擊、格擋、招架、閃避、未命中容易區分；完全避免把 0 傷害顯示成實際傷害。
- 事件與快照快速連續抵達時，目標不會因卡片重繪而把效果播到錯誤單位。
- 戰鬥結束、切換新戰鬥、切換分頁再回來，不會留下殘留特效或一次播放過期事件。
- 原訊息區仍能完整呈現戰鬥紀錄。

### Phase 2：技能、治療與 AOE

1. 在技能結算實際套用傷害/治療/護盾的位置產生事件，避免只在技能開始時發事件而沒有實際命中結果。
2. AOE 傳送一個事件、多個 `hits`；對同一波攻擊共用一次起手效果，再依目標分散命中反應和數字。
3. 補上有可靠來源的 `damageType`。沒有來源的技能先用 `UNKNOWN`，待資料模型有定義後再補齊。
4. 加上治療數字、護盾提示，以及 DoT/HoT tick（如果這些結算能提供準確目標和數值）。
5. 檢查死亡目標：MVP 先播放該次命中與傷害數字，不急著複製卡片製作死亡殘影；待基本動畫穩定後再處理死亡離場。

**驗收**：單體技能、全體傷害、單體治療、全體治療均顯示正確目標與結算數值；同一個 AOE 不會產生重複的全場起手效果。

### Phase 3：武器與屬性特效

1. 建立小型 `fx-presets` 對照表：先支援斬擊、鈍擊、投射物、法器/施法、徒手。
2. 從事件的 `weaponType` 或 `damageType` 選擇 preset；不要以顯示名稱、ANSI log 或技能 ID 的任意字串猜測動畫。
3. 每種動畫先用 CSS `transform`/`opacity` 做簡潔版本，再決定是否需要 SVG 或 Web Animations API。
4. 在代表性畫面測試：小型與大型敵人、隊員前/後排、視窗尺寸改變、較長名稱、同時多個命中。

**驗收**：不同武器類別與主要法術屬性可以辨認，但畫面不會因每次普攻都觸發多個高亮/震動而變得刺眼或難讀。

### Phase 4：擴充與打磨（獨立排期）

- 若遊戲設計確認「一排」的定義，新增後端目標選擇規則及測試；事件的 `hits` 傳回實際中招目標。現有敵方重力下落的視覺排位不等於後端目標規則，需特別對齊。
- 若要增加我方暴擊或未命中，先定義機率、命中模型、裝備/屬性影響與平衡測試，再讓表現層使用新判定。
- 依玩家偏好增加「完整/精簡/關閉」設定、音效、全場震動、死亡動畫等。這些不是 MVP 的前置工作。
- 對手機/低效能裝置限制特效數量及同時動畫，並觀察實際遊戲中的訊息與事件頻率。

## 7. 測試與驗收清單

### 後端

- 普攻事件的 actor、target、武器類型、最終傷害與狀態變化一致。
- `DefenseResolver` 的六類 outcome 均可正確序列化；格擋殘傷與完全閃避不混淆。
- AOE 對每個實際命中對象只產生一次 hit；死亡、DoT、反擊不重複加算同一份傷害。
- 單一事件批次的排序、`battleId`、`seq` 正確；手動技能、勝敗結算及取消路徑不漏送事件。
- DTO 的未知/空欄位有明確處理，不因可選動畫欄位缺漏而中斷戰鬥或 WebSocket 狀態傳送。

### 前端

- 對事件範例逐一驗證：物理命中、暴擊、格擋殘傷、完全格擋、招架反擊、閃避、未命中、AOE、治療。
- 命中結果的文字與顏色/大小同時可辨識；低對比與色覺差異不會讓狀態只剩顏色區分。
- 同一 tick 多事件、相同目標連續受擊、目標死亡並重繪、不同尺寸卡片、畫面 resize 均正確定位。
- `prefers-reduced-motion` 下仍看得到數字和文字結果；FX layer 不攔截點選。
- 戰鬥結束後清空事件計時器與 DOM 元素；hidden 分頁不累積等待播放的大量事件。

### 人工試玩

1. 一般戰鬥連續觀察至少數分鐘，確認動畫頻率不影響閱讀戰鬥 log。
2. 觸發有格擋/閃避/招架機會的隊員，確認其防禦動畫和 log 相符。
3. 使用可取得的單體、AOE、治療技能，比對畫面目標與 HP 實際變化。
4. 連續切換戰場、視窗寬度與瀏覽器分頁，確認沒有卡死、錯位或舊動畫重播。
5. 用瀏覽器效能工具檢查大量同時命中時是否出現長任務或明顯版面重排。

## 8. 主要風險與處理

| 風險 | 可能結果 | 建議處理 |
|---|---|---|
| 事件只在自動戰鬥迴圈發送 | 手動施放技能的畫面更新延遲或沒有動畫 | 事件在實際結算路徑產生；共用發佈器或明確 flush 手動動作 |
| 以 index 對 DOM | 目標重排後動畫出現在別的單位 | 以 battle ID + side + 穩定單位 ID 定位 |
| 前端自行決定 AOE/排目標 | 視覺目標與實際扣血不一致 | 後端列出實際 hits，前端只演出 |
| 事件與快照到達順序不同 | 目標卡片已重繪或消失 | 事件播放時重新查 DOM；缺目標時略過演出但保留狀態快照 |
| 前端根據 log 推斷資料 | 格式或語系變更造成錯誤分類 | 從結算結果輸出欄位，不做文字解析 |
| 新增暴擊/一排攻擊混在演出工作 | 悄悄改變戰鬥難度或目標規則 | 視為獨立遊戲機制工作項目，先定規則、再實作 |
| AOE/高攻速效果太密 | 數字遮住角色，動畫掉幀 | 批次合併、錯開播放、設定佇列和同時元素上限 |
| 過度閃光/震動 | 造成不適或偏離原本畫面風格 | 不用全場閃白作為預設，提供減少動態相容行為 |

## 9. 建議落地順序

1. 先做 **Phase 0 + Phase 1**，驗證結構化事件與目標定位可靠。
2. 讓玩家試玩 MVP，優先調整數字大小、停留時間、傷害色彩和動畫頻率。
3. 再做 **Phase 2**，確保技能與 AOE 數值正確。
4. 需求確定後才做 **Phase 3** 的細緻武器/元素特效。
5. 把「一整排」、新增暴擊/未命中、音效與全螢幕演出拆成獨立選項或工作項目，逐項確認是否值得其規則與維護成本。

這樣的順序讓第一版已經能回答玩家最關心的三件事：**誰打了誰、結果是什麼、數值是多少**；之後再用武器和法術外觀增加風格，而不會先投入大量特效卻仍不知道畫面事件和實際戰鬥結果是否一致。
